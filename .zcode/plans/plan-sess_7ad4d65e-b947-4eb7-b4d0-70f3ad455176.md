# 日志与错误检查后台页面 实施方案

## 目标

为上线后的检查与复盘优化提供完整数据面与页面：**失败请求可按 request_id 精确追溯（集成侧联调用）**、失败轮次/任务/升级事件可分类排查、多轮会话可完整回放。三个已确认的决策：请求日志只记失败请求；包含会话回放；升级记录为只读列表。

## 一、后端

### 1. 新增 `request_error_log` 表（alembic 迁移 0019）

- 列：`id uuid PK`、`request_id varchar(128)`、`method varchar(10)`、`path text`（不含 query，防敏感信息）、`status_code int`、`error_code varchar(100)`、`message text`、`detail jsonb`（validation fields / 异常堆栈截断 ~8000 字 / ApiError.details）、`created_at`
- 索引：`(created_at DESC)`、`request_id`、`status_code`
- 同一迁移加 `ix_task_record_status_created (status, created_at DESC)`（全局任务列表用）

### 2. 失败请求捕获：`app/observability/recorder.py` + 改 `app/main.py`

- 新模块 `app/observability/`（`recorder.py` + `repository.py`），与现有域模块布局一致
- 在 main.py 的四个异常处理器（ApiError / RequestValidationError / 未捕获 Exception）中 best-effort 落库（`request.app.state.resources.database` 取引擎，try/except 吞错只打 warning，绝不影响响应）；未捕获异常额外记录 traceback
- 新增 `starlette.http_exception.HTTPException` 处理器：既捕获 404/405 落库，也顺带把 404 响应统一成 `{error:{code,message,details,request_id}}` 格式（当前 404 没有 request_id，集成侧无法追溯）
- 排除 `/health/*` 探活路径；不记录 Authorization 头内容

### 3. 新端点 `app/api/logs.py`（注册进 `api/router.py`，受 service token 保护）

- `GET /api/v1/logs/request-errors`：过滤 request_id（精确）/ path（模糊）/ status_code / from/to，**limit+offset+total 分页**（本项目首个分页端点，失败日志量可能大，值得做）
- `GET /api/v1/logs/request-errors/{id}`：详情含 detail jsonb（堆栈）
- `GET /api/v1/logs/failure-summary?from&to&kb_id`：复盘聚合——`trace_failures`（rag_trace FAILED 按 `error->>'code'` 分组：code/count/last_seen）+ `request_errors`（按 path+status 分组）+ `request_errors_by_day`
- repository 用裸 SQL（项目惯例）

### 4. `/traces` 增强 + bug fix（`app/api/rag.py`、`app/rag/repository.py`、`app/api/schemas.py`）

- 新过滤参数：`error_code`（`error->>'code'`）、`conversation_id`（已有 `ix_rag_trace_conversation_created` 索引）
- **修复 bug**：`RagTraceResponse`/`TraceSummaryResponse` 的 `response_type` Literal 缺 `NEED_MORE_INFORMATION`（0018 已入库该值，一旦查到就会 500）

### 5. Support 失败信息补全（`app/support/repository.py` fail_turn、`app/support/service.py`、`app/support/validator.py`）

- `fail_turn` 对齐 legacy `RagRepository.fail_turn`（rag/repository.py:693-713）：error JSON 增加 `stage/retryable/detail`，service.py:507-514 把 `LlmError.detail/retryable`（上游 HTTP 状态等）传进去
- validator.py 各失败分支给 ApiError 加 `details`（违规 section 标题/类型、越界 evidence id、文档外 IP 等）；`_failure_trace` 把 details 与被拒 draft 摘要（sections 的 title/type/evidence ids、image_ids、workflow_update）写入 trace JSON，便于复盘"模型当时想输出什么"

### 6. 其他端点补全

- `GET /api/v1/tasks` 全局任务列表（status/kb_id/from/to/limit），失败任务不再只能按索引查
- `/conversations/{id}/messages` 与 `MessageResponse` 补暴露已存在但未查的列：`content_blocks/response_type/support_mode`

### 7. 日志保留期清理

- `Settings` 加 `request_error_log_retention_days`（默认 30，`.env.example` 补注释）
- worker.py 启动流程（与 index GC 并列，worker.py:27-30）调用 observability repository 的 `delete_expired_request_error_logs`

## 二、前端

### 8. 新视图 `src/views/LogsView.vue`（挂 Diagnostics 菜单组，与 Trace/Playground 并列）

- 顶部概览：MetricCard 行（范围内失败轮次数、请求错误数、Top 错误码）+ 失败分布表（failure-summary）
- `el-tabs` 四个页签（照 ConfigurationView 的 tabs 惯例）：
  1. **请求错误**：过滤栏（request_id 搜索、path、status、时间范围）+ el-table + el-pagination，行点击开 drawer：request_id 可复制、method/path/status/code/时间 + detail JSON 用 CodeBlock（含堆栈）
  2. **失败轮次**：`/traces?status=FAILED` + error_code 下拉，行点击复用现有共享 trace drawer（`store.openTrace`），不重造详情
  3. **任务失败**：`/tasks?status=FAILED` 表格 + drawer（error_code/error_message/stage/attempt/metadata，关联索引可跳转 IndexBuildView）
  4. **升级记录**：`/traces?response_type=ESCALATION_REQUIRED` 表格 + drawer 渲染 trace 内 `escalation.summary`（problem_code/current_step/completed_steps/observations/checks_performed/missing_information）+「查看会话」入口
- 注册：App.vue `menuGroups` Diagnostics 加 `{key:"logs", label:"日志与错误"}` + AdminStudio.vue views map；API 方法加 `admin.ts`、类型加 `types/admin.ts`；组件局部 loading 照 TracesView 模式

### 9. 会话回放：新组件 `src/components/ConversationTimeline.vue`（共享 drawer）

- 由 conversation_id 并行拉 messages（补列后）+ `/traces?conversation_id=`，按轮渲染：消息内容、response_type/support_mode 徽章（复用 StatusBadge）、聚焦文档、每轮 workflow_before/after 状态变化、升级事件高亮
- 入口：TracesView 详情、LogsView 失败轮次/升级记录详情的「查看会话」按钮；drawer 开关状态放 adminStore（两处共享）

## 三、测试与验收

- 后端：observability recorder 落库（含 best-effort 不影响响应）、logs API 过滤/分页/聚合、全局 tasks 端点、traces 新过滤参数、message 新列、support fail_turn 完整错误载荷、validator details、404 响应格式；新表进现有 PG 集成测试
- 前端：views.spec.ts 冒烟数组加 `logs`；viewInteractions.spec.ts 加 LogsView 各页签/ConversationTimeline 用例；admin-api.spec.ts 补新方法
- 收尾跑 `scripts/check.sh`（ruff + mypy strict + pytest ≥80% + 前端 lint/type-check/test/build）

## 实施顺序

迁移 0019 → observability 模块 + main.py 捕获 → logs/traces/tasks/messages 端点 → support 失败补全 → 保留期清理 → 前端 API/类型 → LogsView + ConversationTimeline + 菜单注册 → 测试补齐 → check.sh 全绿

不做的（明确排除）：全量请求日志、升级工单流转、持久化 stdout 结构化日志（失败请求已覆盖排障主场景；接入 ELK 等留待集成侧确定后）
