# LLM2 思考模式与已有文档卡片实验

日期：2026-10-09。仅本地固定输入实验；未接入业务链路，未部署生产。

## 结论

复用 2026-10-08 的 45 次证据输入实验，不重跑原版基线。选用五题的实际多文档全文 A，以及 LRU 正确单文档全文 B，共六组输入、18 个历史回答。新增两个独立方向各三次重复：思考 18 个样本、已有卡片 18 个样本，共 36 个生成结果；既有结构修复使实际供应商请求为 40 次。

**没有观察到足够稳定的整体改善，不建议开启生产思考或直接把现有卡片附给 LLM2。** 思考组最终返回有效结构 16/18，另外两次结构化输出失败；卡片组返回 18/18。这是运行结果，不是回答正确率。

- MU：思考仍有开盖/内部检查和未经核验的判断；卡片有两次更贴近不开盖观察，但第三次又称开盖是必要诊断，并扩大电压/因果判断，未稳定解决。
- PDC：两个方向仍展开应急接线、申请更换等维修流程；卡片第一轮出现“无论当前状态如何，只要存在氧化……”的泛化，未复制原人工片段组的局部收益。
- LRU：正确线缆文档 B 下两组各三次仍答“五分钟”。思考 A 有一次识别到五分钟属于重新开机之后，却推断“可直接进行拆卸更换”，仍是错误前提/许可判断，不能算修复。
- FFC：正确电脑地址及“不能仅凭端口掉线确诊”保留，但仍借用邻近更换文档的 Ping/离线流程；没有新增正确能力。
- PSU：核心更换步骤保留。思考更详细、配图更多，但引入了板卡更换的条件和部件名称混用；不是完整安全性或逐图验收。

没有运行 Golden Set、质量断言、模型评委。对成功返回的 34 个完整回答逐条阅读正文与后续建议，核对源文档；两次失败不补跑漂亮样本，也不假定其未采集到的正文正确。

## 控制与实验边界

同一知识库 `5ae9881a-a568-436b-9330-2da5e9a2a9c9`、同一冻结索引 `7b23aee9-f828-4ee6-b282-7de05bf0d283`，真实 DashScope `qwen3.8-flash`。原问题、空历史、产品档案、`IN_SCOPE/KNOWLEDGE`、决策规则、输出 Schema、完整正文、图片绑定及原提示词均与历史输入一致，重新计算 SHA256 后再付费调用。

不调用 LLM1、Embedding 或 Rerank，不创建 Assistant 会话，不写模型配置、卡片、索引或源文档；不测试检索自动选材、历史、公开组装及端到端效果。之前 C 是人工片段或空输入，本次不重复它们，避免将卡片/思考与删正文混在一起。LRU A/B 同时保留，单独比较每组自己的历史回答，不用 A/B 差异证明文档数量收益。

| 方向 | 输入/配置变化 | 未改变项 |
| --- | --- | --- |
| THINKING | 原提示词逐字不变，`enable_thinking=true`，既有预算 2048 | 全文、图片、规则、温度 0.1、输出上限 4096、单请求超时 45 秒 |
| CARDS | 原 JSON 仅增加 `document_guidance`：同文档 D key 对应的既有类型、摘要、任务、前提、排除范围 | 思考关闭、正文不删改、图片不删改、规则/Schema/生成参数不变 |

没有同时开启思考和附卡片。卡片信息只是新增数据，没有另写针对某题的使用规则或预期答案；没有在实验前修改或重新生成卡片。未加入 `applicable_questions` 等长问题列表，避免把整份卡片当成新的问答任务。结果只代表这次五字段呈现方法，不证明所有卡片组织方式无效。

原版适配器在 Qwen 思考开启时会关闭供应商 JSON Mode，保留 Prompt Schema、本地校验及既有一次结构重试。因此这测试的是项目现有思考开关的完整行为，不是“只多出思考 Token、其他传输字段绝对不变”。实际请求元数据证明：18 个思考样本均请求开启，最后返回的 usage 均有正 reasoning_tokens；卡片组均关闭并使用 JSON Mode。没有保存或开启思考正文日志。

两个方向交错运行、最多并行两对样本，奇偶交替先后顺序；每题三个重复不能完全对半，但全体平衡。未设 seed。复用的是跨日历史控制，不能冻结供应商内部模型修订、缓存或网络状态；输入哈希一致不等于同期随机配对。因此不能据此证明生产延迟改善或总体准确率变化。

## 已有卡片核验

涉及 13 份卡片，均为 READY、CONFIRMED、Schema v1、revision 2。未将“已确认”当作事实质量认证。

预检最初拒绝了当前算法下不匹配的指纹；只读核对 Git 历史后确认，它们保存的是 `0620446` 的旧算法（包含 index_id）。13 份均与该旧算法基于当前同一索引/原文重新计算的结果完全一致，不是直接忽略指纹校验。实验工具同时验证当前算法或这个明确的历史算法；数据库指纹未更新，没有执行卡片迁移/自愈。

人工阅读发现：

- PDC 检查卡片把“吹干、临时对接、更换”列成任务，没有携带原文对应的“有水渍”“腐蚀严重”等条件；前提反而列出吹干/对接工具。这种概括不足以给最终模型提供更清晰的适用边界。
- LRU 检查卡片列出了重新插拔、确认报警和申请更换，但未明确等待时间属于恢复后的观察阶段。
- MU 卡片写明需要打开六螺丝盖板，却未形成“不拆机观察”的适用说明；另有任务文字将核心板灯的判断写为核心板故障，而源文档对应句写的是底板。原文是否有笔误待专业核验，不能由自动卡片静默纠正。
- PDC 更换卡片另把 PDC 展开为“电源分配单元”，当前更换原文未提供这个定义。本次未据此确认正式产品含义，也未修改卡片。

所以“把已有卡片再传一次”不等同于补上高质量边界：卡片可能已有信息，但也可能丢失条件、扩大解释。这里没有证明上述卡片问题是所有错误的唯一原因。

## 逐题重复结果

### MU：不拆机，仅观察与记录

历史 A 三次都越过观察边界。源文档为 MU 报警后的内部自查，明确开盖六颗螺丝；不支持把组件标识或图片示例读数当整机输入范围和正常阈值。

| 重复 | THINKING | CARDS |
| --- | --- | --- |
| 1 | 两次结构尝试后 `STRUCTURED_OUTPUT_INVALID`，61.884 秒 | 主要给外部记录，但推断 OPU 通道显示/数据刷新、硬复位/故障原因，且扩至未来开盖/厂家支持；不是经产品资料验证的完整方案 |
| 2 | 要拧开六颗螺丝观察板卡灯、机箱内部 PSU/保险丝，仍违反当前限制 | 主体避免直接开盖，但引用组件 18–36VDC，推断外部接口/灯态及故障概率；未充分区分部件事实和整机事实 |
| 3 | 第二次结构尝试才成功；正文侧重不开盖，但仍给未核验 24V 阈值、启动时间/网络因果判断，后续扩到开盖排查 | 明确称开盖是必要诊断，把“不拆机”缩为“不拆板”；由照片 25/26V 扩成 24–27V 正常范围，后续又提 PSU 输出测量 |

卡片前两次有局部收敛，第三次反转；思考没有稳定守住任务边界。不能以“正文更长、有表格、后面有免责声明”证明改善。

### PDC：氧化、通信正常，评估是否需要专业检查

历史 A 仍有维修流程牵引；原人工片段 C 三次较聚焦，但未经过工程安全验收。原文仅在水渍/严重腐蚀前提下分别吹干/临时对接。

| 重复 | THINKING | CARDS |
| --- | --- | --- |
| 1 | 条件表里展开对接/必须更换；主张即使功能正常发现腐蚀就按文档申请更换，扩成处置流程 | 明确声称文档要求“无论当前状态如何，只要存在氧化或潜在进水风险”申请更换，超出当前证据 |
| 2 | 先按检查结果分支，后又要求申请备件、下次维护更换；电压正常与连接可靠的推断过强 | 有轻微/严重分支，但仍展开接线、临时对接，且后续建议继续维修流程 |
| 3 | 两次结构尝试后 `STRUCTURED_OUTPUT_INVALID`，51.247 秒 | 加入未核验 24V±5% 判据、触摸端子等建议；再给对接/更换流程。结尾安全提示不足以验证这些操作 |

没有观察到任一方向稳定达到人工片段 C 的收敛效果，不建议照现状附卡片。不能把失败正文当作当前真实现场操作指导。

### FFC：电脑 IP 与硬件诊断边界

两方向各三次都正确答电脑 `172.16.8.175` / 掩码 `255.255.255.0`，不能仅凭交换机端口掉线确诊。历史 A 已有这些正确答案，不计为新增收益。

两方向都仍把邻近文档的设备 `.100` Ping/离线/更换流程带入第二点。思考第二次还需结构重试才成功。一般原因列表也混入 IP 配置/冲突等，不能当作已验证的该设备物理掉线原因。未展开软件升级，但没有稳定消除不必要的邻近流程。

### PSU：完整操作与图片

两方向各三次保留定位、检查、断电、拆下 3359 核心板/底板、更换 PSU、装回接线、拍照标记及开机后五分钟观察报警的核心内容。

- 思考三次均更详细，采用补充板卡文档的六螺丝盖板、四螺丝固定和接线标记等，均有七个图片标记。补充展开有依据的部分是可见变化，不以更多图片自动计为更好。
- 思考还引入核心板更换/历史 APT 的说明；它只适用于实际更换核心板，不能因 PSU 更换时拆装原核心板就认为必须导入。第三次写“仅更换 PSU 底板”，而相关原文说的是“更换 3359 底板”，存在部件名称迁移。细化步骤是否完整、安全及逐图像素对应仍需专业核验。
- 卡片组三次均有五个图片标记，核心回答与历史 A 接近；第一轮后续又问是否需要更新核心板配置/历史数据，另外两次没有后续扩展，不能宣布稳定消除了牵引。

没有运行 Assistant 图片组装、浏览器显示或独立工程评审，不宣称完整操作/配图已验收。

## 可用性与开销

| 项目 | 复用历史控制 | THINKING | CARDS |
| --- | --- | --- | --- |
| 生成样本 | 18 | 18 | 18 |
| 有效结构返回 | 18 | 16 | 18 |
| 供应商请求 | 历史每样本一次 | 22 | 18 |
| 两次结构尝试后失败 | 0 | 2（MU1、PDC3） | 0 |
| 成功样本经历结构重试 | 0 | 2（MU3、FFC2） | 0 |
| 全部样本采集延迟中位数 | 6.927 秒 | 21.247 秒 | 5.693 秒 |
| 最长样本 | 不据历史推断当前上界 | 61.884 秒 | 17.062 秒 |

既有单次请求超时仍为 45 秒；完整结构重试可使一个生成样本超过 45 秒，并非本次偷偷放宽时限。思考开启同时关闭供应商 JSON Mode，所以两次结构失败不能单独归因为模型推理本身；错误正文未采集，不推断具体 JSON 字段出错原因。

最后一次返回的 usage 汇总：思考输入 181958、completion 19676、其中 reasoning 11341；卡片输入 188670、completion 6951。重试覆盖此前 usage，所以思考汇总**不等于全部供应商用量/费用**，reasoning 也不再额外加到 completion。卡片加入信息提高对应输入 Token；跨日基线、缓存、网络、输出长度及重试影响延迟，不把卡片中位数更低解释为生产提速。
