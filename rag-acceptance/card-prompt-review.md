# 文档卡片提示词 v1 → v2（2026-10-09，四个预设关卡全部通过）

## 结论

新提示词（`rag-document-card-v2`）解决了此前在“思考与已有卡片”实验里观察到的三个缺陷，四个预先写定的关卡全部通过：

| 缺陷 | v1 | v2 |
| --- | --- | --- |
| 条件操作的触发条件丢失 | 动作类任务带条件词 4/29（14%） | 15/30（50%）；PDC 检查文档的“若有水渍则吹干 / 若腐蚀严重则临时对接”在两次生成里都保留 |
| `prerequisites` 没有定义，工具被当成前提 | 11 条工具、备件、准备类前提 | 2 条 |
| 凭空展开缩写 | PDC 更换文档两次生成里把 PDC 展开成**两个互相矛盾的名字**（“电源分配控制器”“位置数据转换器”） | 0 次 |

这只改善新生成卡片的质量。**卡片不进入 LLM 2**（只用于召回和文档级 Rerank 的输入），所以它不会修复 LRU/PDC/MU 一类回答的适用性问题。

## 设计

- 对象：`DocumentCardGenerator` 的系统提示词和 `DocumentCardPayload` 的字段描述；`DOCUMENT_CARD_PROMPT_VERSION` 从 `v1` 升到 `v2`。版本号只写入生成元数据（`prompt_version`、`prompt_hash`），没有任何逻辑用它判断卡片过期，所以升版本不会让已确认的卡片失效。
- 新增规则（措辞通用，不含任何文档或产品名）：带条件的操作必须连同条件写进 `tasks` 和 `summary`，不得写成无条件任务，也不要自行概括成“一律”“必须”；`prerequisites` 只写适用前提（设备、状态、现象、阶段），不写工具、备件或准备工作；产品名、型号、缩写按正文原样使用，正文没有给出全称时不要展开或猜测。`tasks`、`prerequisites` 的字段描述同步说明，因为 JSON Schema 会随系统提示词一起交给模型。
- 实验：`run_card_prompt_review.py`。同一批 13 份文档（此前实验检查过其卡片的那 13 份），OLD（git `HEAD`，v1）对 NEW（工作区，v2），各生成 2 次，共 52 次真实调用（`qwen3.8-flash`）。**只生成，不写库**：没有卡片被替换，审核状态不变。
- 判读规则在首次付费调用前写入工具的文档字符串，结果出来后没有调整。

## 关卡与结果

| 关卡 | 规则 | 结果 |
| --- | --- | --- |
| 1 有效性 | NEW 的生成错误不超过 OLD +1 | 通过：两边都是 26/26 成功、0 错误 |
| 2 条件保留 | 机械筛查：带动作的任务中带条件词的占比 NEW 高于 OLD；并且阅读被点名文档的卡片，NEW 写出了 OLD 丢掉的触发条件 | 通过：14% → 50%；阅读确认见下 |
| 3 前提 | 工具、备件、准备类前提 NEW 少于 OLD | 通过：11 → 2 |
| 4 无凭空展开 | NEW 卡片不含源文档没有的展开 | 通过：OLD 2 次、NEW 0 次 |

阅读确认（节选）：

- **PDC 检查接线盒（文档 9）**：源文档“如有水渍则拆下吹干；如腐蚀严重则临时对接”。OLD 把它合并成无条件的“执行吹干处理或临时对接端子排以恢复功能”，前提里还写了源文档没有的“具备万用表”。NEW 两次都拆成“若接线盒内有水渍，拆下接线板吹干”和“若腐蚀严重，临时对接”，前提改为“PDC 出现报警或疑似接线盒故障”等现象。源文档本身无条件的最后一步“做好水密防水并申请新接线盒更换”，NEW 仍写成无条件，忠实于原文。
- **MU 报警板卡自查（文档 3）**：源文档“如果 2 处灯不闪烁，则 3359 通讯底板有问题”。OLD 概括为“观察并判断通讯指示灯工作状态”，条件全部丢失。NEW 保留了“若灯不闪烁则判定为……”，并原样沿用源文档措辞（没有悄悄“纠正”它可能的笔误）。
- **LRU 检查通讯线缆（文档 17）**：源文档唯一的条件“如故障依旧则申请备件更换”，OLD 和 NEW 都保留；前提从“具备打开 MU 机箱的操作权限或工具”变成“设备出现 DAU 报警”。
- **PDC 更换（文档 10）**：这篇没有条件步骤。OLD 的两次生成把 PDC 展开成两个互相矛盾的名字，NEW 没有。

## 副作用与残留（不属于预设关卡，但应该知道）

- **新卡片会自行加注释**：MU 报警板卡文档的两次 NEW 生成里，第 3 处灯的那条任务都带了一句“（注：原文此处表述可能指代核心板或底板异常，……）”，OLD 为 0。源文档里 3 处灯不闪烁却写成“3359 通讯底板有问题”，很可能是笔误；卡片保留了原文措辞，并加上了模型自己的怀疑。这句话不在源文档里，会进入卡片的路由文本。它对审核者可能有用（能提示原文疑点），但属于模型自行加入的内容。是否需要收紧第 6 条规则或在生成器里去掉注释，没有处理。
- **残留 2 条工具类前提**：PDC 更换文档第 2 次生成列出“万用表、大十字螺丝刀……”，而该文档的第一步本来就是“准备工具：……”；升级 LRU 文档第 2 次生成列出“……及 3359 核心板备件”，我没有核对源文档是否支持。
- **摘要偶有混淆**：PDC 检查文档第 1 次 NEW 的摘要写成“在发现水渍或腐蚀时执行临时对接修复”，把“水渍→吹干”和“腐蚀严重→临时对接”合在了一起，任务层面是对的。
- document_type 在 1 个成对样本里不同，不影响结论。

## 局限

13 份文档，每份只有 150–1,100 字，各生成 2 次（温度 0）；评阅人是同一个开发代理、非盲评；机械筛查只是近似（“带条件词的占比”里，源文档本身无条件的步骤如“申请新接线盒更换”也算在分母里，所以 50% 不是上限）；只验证了生成质量，没有验证对召回和 Rerank 的影响。

## 上线注意

已有卡片不会因此改变，`v2` 只用于新生成或显式重新生成的卡片。已确认的卡片默认不会被自动生成覆盖；显式替换成功后卡片回到待确认状态，已上线的知识库会因此暂时 `ready=false`，直到重新确认。所以不建议整库重生成：只对受影响的几份文档（PDC 检查与更换、LRU 检查、MU 板卡自查等）在维护窗口里重新生成并逐份审核，审核时顺便检查上面提到的“注”。

## 复现

```bash
# 零付费预检；输出路径必须不存在
PYTHONPATH=backend .venv/bin/python rag-acceptance/run_card_prompt_review.py \
  --prepare-only --output rag-acceptance/reports/card-prompt-recheck.json

# 真实付费对照（--ref 指定 OLD 版本的 git 引用；默认 HEAD，即工作区改动之前的提交）
PYTHONPATH=backend .venv/bin/python rag-acceptance/run_card_prompt_review.py \
  --ref fbb9d92 --repeats 2 --concurrency 2 --output rag-acceptance/reports/card-prompt-repeat.json

# 汇总，并查看某份文档的卡片
PYTHONPATH=backend .venv/bin/python rag-acceptance/run_card_prompt_review.py \
  --summarize rag-acceptance/reports/card-prompt-20261009/answers.json --show "PDC 如何检查"
```

原始结果在 Git 忽略目录 `reports/card-prompt-20261009/`（`prepared.json`、`answers.json`）。
