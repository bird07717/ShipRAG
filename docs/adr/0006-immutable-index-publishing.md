# ADR-0006：不可变 Active Index 与全量快照发布

- 状态：接受
- 日期：2026-08-17

## 背景

产品要求知识库重建期间不影响在线回答，并采用双索引切换。如果直接在 Active Index 中增加、删除或重新生成 Chunk，在线请求会在处理过程中观察到部分更新、缺失向量或新旧策略混合。

V1 不提供用户可见的历史版本管理，但内部仍需要索引快照来保证一致发布。

## 决策

1. Active Index 发布后不可变。
2. 每次生效变更通过新的全量 Knowledge Index 构建：
   - 冻结当前未删除 Document Source 快照；
   - 为每份文档生成 Index Document、Element、Chunk、图片结果和 Embedding；
   - 构建 BM25 与向量索引；
   - 执行完整性检查；
   - 进入 `READY`；
   - 事务原子切换。
3. 同一知识库最多一个 BUILDING Index。
4. 构建期间的新变更设置 `rebuild_required=true`，不修改当前快照；当前构建终止后自动合并启动下一构建。
5. `activate_on_success=true` 为普通上传和重建的默认行为；RAG Studio 可以创建 `READY` 后手动激活的构建。
6. 激活失败必须完整回滚，旧 Active Index 继续服务。
7. 失败构建保留用于诊断；重试创建新索引，不复用失败 ID。
8. 旧索引切换为 `DEPRECATED` 后异步清理，不能在激活事务内执行大批删除。

## 请求一致性

Chat 在请求开始时读取并冻结 `active_index_id`。本次请求全程使用该 ID，即使中途发生激活；下一个请求才使用新索引。

所有在线检索必须包含：

```text
kb_id = requested knowledge_id
index_id = frozen active_index_id
```

## 并发控制

构建协调器在请求构建和激活时锁定 Knowledge Base 行或使用等价的数据库互斥机制。数据库还应通过部分唯一索引保护：

- 每个知识库最多一个 `BUILDING`；
- 每个知识库最多一个 `ACTIVE`。

应用锁不是数据库约束的替代品。

## 清理策略

M1/M6 通过配置冻结保留数量或保留天数。清理前必须确认：

- 索引状态为 `DEPRECATED` 或 `FAILED`；
- 不是任何 Knowledge Base 的 `active_index_id`；
- 没有运行中的任务；
- 已超过并发请求安全窗口；
- 数据库行和 MinIO 派生资产属于精确目标 `index_id`。

## 后果

### 正面

- 在线请求永远看到完整一致的索引快照。
- 构建失败不影响现有服务。
- Chunk 策略、模型和维度升级可以随索引一起原子发布。
- Trace 可以明确记录实际使用的索引版本。

### 代价

- 全量重建消耗更多模型额度、时间和临时存储。
- 文档删除或上传不会立刻影响在线检索，要等新索引发布。
- 高频变更需要请求合并，仍可能连续触发两次构建。

## 暂不采用

- Active Index 原地增量更新：发布边界不清晰，失败恢复复杂。
- Chunk 级 Copy-on-write：可减少重算，但增加引用共享、清理和模型版本一致性复杂度；可在 V1 稳定后通过新 ADR 引入。
- 用户可见版本管理：超出 V1 范围；内部索引版本只服务于发布与诊断。
