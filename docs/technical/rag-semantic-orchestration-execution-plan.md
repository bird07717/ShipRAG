## 一、执行结论

当前不再继续通过单独降低 Chunk 阈值、扩充问法正则或为个别文档增加硬编码来解决首轮命中和回答形式问题。实施方向调整为：

1. 在现有 Chunk 级索引之外增加 RAG 专属文档卡片和文档级检索，直接表达一份文档解决的任务、适用对象、文档类型和排除范围。
2. 使用两个职责不同的在线 LLM 阶段：LLM 1 负责查询理解、上下文还原和检索规划；LLM 2 负责候选文档判断、证据等级、回答策略及必要的最终生成。
3. 原始问题检索与 LLM 1 尽量并行开始；LLM 2 同时完成决策和生成，不再增加第三次在线生成调用。
4. 回答策略不再二分为“交付文档/没有文档”，而是明确区分局部短答、完整文档、文档辅助回答、通用工程回答、澄清和范围外。
5. “文档优先”定义为：任务级问题与完整操作文档直接匹配时，即使用户没有写“完整”也优先交付原文；明确的参数、位置和单步骤问题仍短答。
6. 结构化问题状态保存用户目标、已确认事实、已执行操作、观察结果和待确认条件；模型假设不得写成用户事实。
7. 继续使用现有 Assistant 请求、SSE、响应类型、引用、图片、历史和幂等契约；新增内容只属于内部 RAG 编排、管理 API 和 Trace。
8. 新能力必须独立开关、先 Shadow、再测试环境 Enabled、最后按真实质量门槛启用；关闭开关即可恢复现有路由，不回滚文档、索引或历史数据。

本计划在 RAG 范围内取代 ADR-0002“热路径不使用在线 LLM 仲裁”的限制，并扩展 ADR-0017 的确定性回答形式与轻量 `rag_issue`。`shadow` 只生成内部 P2 候选和 P3 响应计划诊断，公开回答仍由 ADR-0017 与旧路径决定；P3 的 `enabled` 接管能力已经实现，但只有完整放行门槛通过后才可用于生产。

## 二、当前基线与结构性问题

### 2.1 可保留的现有能力

以下现有能力继续复用，不重写基础设施：

- 会话冻结知识库、活动索引和模型快照。
- 向量检索、BM25、RRF 融合、Rerank 和邻接 Chunk 扩展。
- Rerank 输入拼接最新 `document_source.display_name`。
- 原始 DOCX 的文本、表格和图片结构化交付。
- 长文档完整交付与模型输入预算分离。
- `DOC_QA`、`CHUNK_QA`、`DOMAIN_ASSIST` 的事实/推断边界。
- 完整问答轮次、焦点代次、失败终态、幂等重放和公开响应快照。
- Assistant 独立凭据、用户隔离、知识库上线边界和外部字段过滤。
- Trace、回答优化、复测和 Golden 执行工具。

### 2.2 当前结构性问题

当前在线链路先通过 Chunk 级分数和固定规则选文档，再用正则判断回答形式，最后才把已确定的上下文交给生成模型。造成：

- Chunk 最适合找局部证据，却承担了判断整份文档是否覆盖用户任务的职责。
- 文档聚合领先仍可能因单 Chunk 下限失败；降低全局下限又会增加错误文档交付。
- LLM 能理解用户任务，却不能修改已经完成的 `NO_MATCH`、`CLARIFY` 或回答形式决策。
- 知识库有部分证据时，文档问答和通用工程分析仍是割裂分支，不能稳定形成“文档事实 + 工程推理”。
- `rag_issue` 只保存原问题和一个条件；通用回答后未必建立状态，连续排查仍大量依赖普通历史重新猜测。
- 文档显示名称能够改善候选标题和 Rerank，但改名不改变既有 Chunk 向量、BM25 `search_text`，不能承担语义编排职责。

2026-09-13 真实 Assistant 小样本为 5 类 6 轮、自动断言 4/5，p50 10.294 秒、p95/最大值 35.681 秒。其中“请给出配置 VAU 图像的完整步骤”目标文档聚合分明显领先，但最佳 Chunk 0.6103 低于 0.70，最终错误进入 `UNCONFIRMED`；局部 IP 问题则能正确短答。该结果证明回答形式本身可行，主要缺口在文档级任务判断和连续编排。

## 三、设计原则与非目标

### 3.1 设计原则

1. **任务适配优先**：先判断用户要完成的任务和问题范围，再决定短答、文档或推理。
2. **文档级选择与 Chunk 级取证分离**：文档卡片解决“哪份文档”，Chunk 解决“哪段证据”。
3. **文档是事实与操作载体，不是回答准入门槛**：没有可靠文档但属于产品范围时，允许通用工程分析。
4. **完整原文不由模型重写**：`DOCUMENT_DELIVERY` 只让模型选择文档，正文、图片和表格由后端读取冻结索引中的原始结构。
5. **模型决策受结构和白名单约束**：模型只能选择本轮候选文档和 Source ID，非法输出失败关闭或回退。
6. **短问题保持短答**：参数、位置、单步骤和明确事实题在证据足够时不倾倒全文。
7. **任务级文档提高优先级**：完整操作文档直接覆盖用户目标时，不要求用户必须出现“完整/全文”关键词。
8. **排查持续推进**：使用用户确认的事实和结果选择下一步，不重复已执行操作，不把模型建议当作已执行事实。
9. **RAG 与 Support 隔离**：不读取 Support Profile、标签、标准问题或工作流；仅复用基础 LLM、检索和公共数据访问组件。
10. **先可观测再替换**：新旧策略必须可在同一输入上对照，任何生产启用都需要明确质量和延迟证据。

### 3.2 非目标

本期不实施：

- GraphRAG、联网搜索、多 Agent、自主执行设备操作或自动创建工单。
- 将 Support Profile 数据复制或直接用于 RAG 决策。
- 让模型修改知识库、发布索引、重命名文档或写入产品参数。
- 全库文档全文一次性塞入 Prompt。
- 修改外部 Assistant API 路径、认证、请求必填字段、SSE 事件名或公开响应类型。
- 追溯重算历史回答、旧 Trace 或幂等终态。
- 用相同模型重复询问同一问题作为“多数投票”；两次调用必须完成不同职责。

## 四、目标架构

```text
用户问题 / Assistant 会话
          │
          ├──────────────► 原始问题向量 + BM25（尽早并行）
          │
          ▼
LLM 1：Query Planner
  - 还原独立问题
  - 新任务/追问/纠正/条件回复
  - 设备、部件、动作、现象
  - LOCAL/TASK/DIAGNOSTIC/EXPLANATION
  - 1～3 条检索查询
          │
          ▼
文档级检索（RAG Document Card） + Chunk 级多查询检索
          │
          ▼
融合、Rerank、候选文档摘要和证据组织
          │
          ▼
LLM 2：Response Planner / Generator
  - 文档 DIRECT/PARTIAL/NONE
  - 策略选择
  - 候选白名单内选文档/Source
  - 短答、文档辅助或通用回答
  - 下一建议与问题状态补丁
          │
          ▼
确定性执行器
  ├─ SHORT_ANSWER ─────────► ANSWERED
  ├─ DOCUMENT_DELIVERY ─────► DOC_DELIVERED（原文、图表、图片）
  ├─ DOCUMENT_ASSISTED ─────► ANSWERED（有据内容 + 工程推理）
  ├─ GENERAL_TECH ──────────► ANSWERED（无伪造引用）
  ├─ CLARIFY ───────────────► UNCONFIRMED
  └─ OUT_OF_SCOPE ──────────► OUT_OF_SCOPE
```

模型输出不能直接改变数据库焦点、引用或响应类型；确定性执行器完成白名单校验、来源验证、公开映射、状态事务和失败收口。

## 五、RAG 文档卡片与文档级检索

### 5.1 定位

新增 RAG 专属 `rag_document_card`，按知识库、冻结索引和文档版本化。不得复用 `document_profile`、`document_problem_profile` 或 Support 发布表，避免重新耦合两条链路。

文档卡片表达整份文档解决什么任务，不复制完整正文。建议内部结构：

```json
{
  "schema_version": 1,
  "document_type": "PROCEDURE",
  "summary": "配置VAU网络图像的完整操作文档",
  "components": ["VAU", "网络图像"],
  "tasks": ["配置VAU图像", "设置电脑网络", "配置图像通道"],
  "applicable_questions": [
    "如何配置VAU图像",
    "VAU图像配置步骤是什么",
    "配置VAU时电脑网络如何设置"
  ],
  "prerequisites": ["电脑与设备网络连接可用"],
  "key_topics": ["电脑IP", "子网掩码", "图像通道"],
  "exclusions": ["VAU线缆硬件故障排查"],
  "has_procedure": true,
  "has_images": true
}
```

`document_type` 首期限定：

- `PROCEDURE`：连续操作、升级、配置、拆装、更换。
- `REFERENCE`：参数、接口、状态、版本和定义。
- `TROUBLESHOOTING`：现象、原因和排查步骤。
- `OVERVIEW`：产品结构、功能和通用说明。
- `MIXED`：无法安全归入单类；不能仅因该类型直接全文交付。

### 5.2 数据约束

实施时新增 Alembic revision（编号以实施时 head 为准），建议字段：

| 字段 | 约束与用途 |
| --- | --- |
| `id` | UUID 主键 |
| `knowledge_id`、`index_id`、`document_id` | 外键并唯一约束 `(index_id, document_id)`；读取必须同时限定三者 |
| `schema_version` | 正整数，支持后续结构升级 |
| `document_type` | 受检查约束的字符串枚举 |
| `card_payload` | JSONB；数组长度、单项长度和总大小由应用层及必要数据库约束共同限制 |
| `routing_text` | 由卡片稳定字段生成的内部检索文本，不直接对外展示 |
| `routing_embedding` | `vector(1024)`，使用该索引冻结的 Embedding 模型生成 |
| `content_fingerprint` | 内容/索引指纹，用于拒绝过期卡片 |
| `generation_status` | `PENDING/READY/FAILED/STALE` |
| `review_status` | `AUTO/CONFIRMED/REJECTED` |
| `revision` | 非负整数，管理编辑乐观并发 |
| `generator_snapshot` | 仅保存 provider/model/prompt 版本、哈希和必要诊断，不保存密钥 |
| `created_at`、`updated_at` | 审计时间 |

显示名称不复制进不可变卡片事实：查询时联接 `document_source.display_name`，使管理端改名立即影响目录、Rerank 和新回答。管理员编辑卡片后只重建该卡片的 `routing_text/routing_embedding`，不重建文档 Chunk 索引。

### 5.3 生成和审核

1. 索引构建完成文档解析后，使用文档标题、章节结构、有限代表片段和图片/流程元数据生成卡片。
2. 生成模型只输出 JSON Schema；任何文档内“忽略规则”等文字均作为数据。
3. 卡片生成失败在新能力 `off/shadow` 时不阻塞现有索引构建；`enabled` 的就绪检查必须报告缺失/过期卡片。
4. 为现有活动索引提供独立回填任务，不重新上传原文，不改变活动索引指针。
5. `AUTO` 卡片可参与 Shadow 和候选召回；生产直接文档交付不能仅依赖未确认卡片，还需 LLM 2 与现有检索证据共同成立。
6. 小体量知识库建议管理员逐份确认卡片；`CONFIRMED` 卡片可作为文档级高置信信号。
7. 文档删除、索引 GC 和知识库删除按外键/维护流程清理卡片；不得阻止既有索引正常回收。

### 5.4 文档级召回

- 使用 LLM 1 的独立问题和检索查询搜索 `routing_embedding`。
- 对当前显示名称、组件、任务和适用问题增加有限 BM25/词法召回。
- 只检索当前知识库和会话冻结索引的 `READY`、非 `REJECTED` 卡片。
- 文档级候选 Top K 首期建议 5；实际默认值需通过当前 VDR600 全量卡片压测确定。
- 文档级分数只用于候选，不直接公开，不单独决定回答。

## 六、LLM 1：查询理解与检索规划

### 6.1 输入

LLM 1 只接收有界数据：

- 当前用户问题。
- 当前 RAG 问题状态。
- 最近有效的完整问答轮次；旧助手回答标为历史建议而非事实。
- 知识库名称和有界公开范围。
- 当前焦点文档的最新显示名称和文档类型（若有效）。
- 系统任务说明；不传凭据、内部地址、管理令牌或无关配置。

原始问题检索可以在 LLM 1 运行时先行执行，避免所有检索都等待规划结果。

### 6.2 输出契约

新增内部 `QueryPlanV1`，建议字段：

```json
{
  "standalone_question": "配置VAU图像时电脑应设置什么IP",
  "conversation_relation": "FOLLOW_UP",
  "intent": "LOCAL_FACT",
  "answer_scope": "LOCAL",
  "product": "VDR600",
  "components": ["VAU"],
  "actions": ["配置"],
  "objects": ["图像", "电脑IP"],
  "symptoms": [],
  "constraints": [],
  "retrieval_queries": [
    "VAU图像配置电脑IP",
    "VAU图像配置网络设置"
  ]
}
```

枚举建议：

- `conversation_relation`：`NEW_TASK/FOLLOW_UP/CORRECTION/CONDITION_REPLY/UNKNOWN`。
- `intent`：`LOCAL_FACT/TASK_PROCEDURE/TROUBLESHOOT/EXPLANATION/REFERENCE/UNKNOWN`。
- `answer_scope`：`LOCAL/TASK/DIAGNOSTIC/EXPLANATORY/UNKNOWN`。

限制：

- `standalone_question` 必须保持原问题语义，不增加型号、参数或用户未提供的事实。
- 最多 3 条检索查询，每条有字符上限并去重。
- 当前用户纠正优先于旧历史；无法确认指代时保留未知，不擅自继承旧设备。
- 输出解析失败、超时或语义校验失败时，保留原始问题作为唯一查询并记录降级，不将失败伪装为成功规划。

## 七、多查询检索、融合与候选组织

### 7.1 检索集合

每轮最多使用：

1. 原始问题。
2. `standalone_question`（与原问题不同时）。
3. LLM 1 生成的最多 3 条去重查询。
4. 有效焦点文档内检索（仅 FOLLOW_UP/CONDITION_REPLY 且焦点仍属于冻结索引）。

每条查询分别执行有界向量/BM25，记录查询来源，再进行跨查询 RRF。不得把同一 Chunk 的多次命中当成多份独立证据抬高文档聚合分。

### 7.2 两级候选

- 文档级候选来自 `rag_document_card`。
- Chunk 级候选来自现有 `document_chunk`。
- 通过 `document_id` 对齐，形成最多 3 份送入 LLM 2 的候选包。
- 候选包包含：最新标题、卡片、文档类型、章节概览、Top Chunk、分数来源、是否当前焦点、是否含流程/图片、卡片审核状态。
- 不把全文目录和全库所有 Chunk 交给 LLM 2。

### 7.3 现有阈值的新职责

`M3_DOC_LOCK_BEST_FLOOR`、聚合分、单强分差和冲突保护继续保留，但改为：

- 高置信直接证据和模型输出校验信号。
- LLM 1/2 失败时的旧路由回退依据。
- Trace 和评测特征。
- 防止 LLM 仅凭标题把不相关文档直接交付的保护条件。

不得再由单一 Chunk 下限否决“文档卡片任务直接匹配 + 多查询证据一致 + LLM 2 选择唯一文档”的结果；新的组合门槛必须以 Shadow 数据确定，不能在计划阶段拍定生产数值。

## 八、LLM 2：证据判断与响应决策

### 8.1 职责

LLM 2 是一次受约束的 Response Planner，同时在需要时生成最终短答或工程分析：

- 判断候选文档与任务是 `DIRECT/PARTIAL/NONE/CONFLICT`。
- 选择回答策略。
- 仅从候选白名单中选择文档 ID 和 Source ID。
- 局部/解释/排查/通用路径直接生成答案，避免第三次模型调用。
- 生成最多 3 条与当前任务直接相关的后续建议。
- 生成受约束的问题状态补丁。

### 8.2 输出契约

新增内部 `ResponsePlanV1`：

```json
{
  "strategy": "SHORT_ANSWER",
  "document_relation": "DIRECT",
  "selected_document_ids": ["候选中的UUID"],
  "selected_source_ids": ["S1"],
  "basis": "DOCUMENT",
  "answer": "电脑IP应设置为172.16.8.175，子网掩码为255.255.255.0。",
  "clarification": null,
  "next_suggestions": [],
  "case_state_patch": {}
}
```

字段限制：

- `strategy`：`SHORT_ANSWER/DOCUMENT_DELIVERY/DOCUMENT_ASSISTED/GENERAL_TECH/CLARIFY/OUT_OF_SCOPE`。
- `basis`：`DOCUMENT/DOCUMENT_AND_GENERAL/GENERAL/NONE`。
- `DOCUMENT_DELIVERY` 只能选择 1 份直接相关文档，`answer` 为空或仅为经过服务端限制的单句定位提示；完整正文由后端构建。
- `SHORT_ANSWER` 和 `DOCUMENT_ASSISTED` 的文档性事实必须引用选中 Source。
- `GENERAL_TECH` 不得选择文档/Source，不返回图片，不虚构正式参数、接线或官方步骤。
- `CLARIFY` 只能询问一个能改变下一步处理的现场条件，不得输出“请选择文档编号”。
- `OUT_OF_SCOPE` 不回答用户原始无关任务。

### 8.3 确定性验证

执行器必须拒绝：

- 不在候选包中的文档或 Source。
- Source 与文档、知识库、冻结索引不一致。
- `DOCUMENT_DELIVERY` 选择删除、失效或不在当前索引中的文档。
- `GENERAL_TECH` 携带文档引用、图片或伪造来源标记。
- `SHORT_ANSWER` 缺少模型声明的文档证据但包含精确产品参数。
- 非法枚举、超长数组、超长澄清、未知字段或无法解析的 JSON。

失败处理：有足够时间时只允许一次格式修复，不重新进行开放式推理；否则使用旧路由或返回现有可重试错误。重试不得创建第二条用户消息、第二个 Assistant 请求或重复推进状态。

## 九、回答策略与文档优先规则

### 9.1 决策矩阵

| 用户范围 | 文档关系/类型 | 目标策略 | 行为 |
| --- | --- | --- | --- |
| `LOCAL` | `DIRECT`，局部证据完整 | `SHORT_ANSWER` | 结论先行，只给必要条件/步骤和实际相关图片 |
| `TASK` | `DIRECT + PROCEDURE` | `DOCUMENT_DELIVERY` | 返回最新加粗标题、完整正文、表格和图片；不要求必须出现“完整” |
| 明确全文/原文 | 唯一有效文档 | `DOCUMENT_DELIVERY` | 用户明确意图优先，仍校验文档归属和有效性 |
| `DIAGNOSTIC` | `DIRECT/PARTIAL` | `DOCUMENT_ASSISTED` | 文档事实 + 通用工程推理；不默认倾倒全文 |
| `EXPLANATORY` | `DIRECT/PARTIAL` | `SHORT_ANSWER` 或 `DOCUMENT_ASSISTED` | 解释事实、推断和通用原理，不输出无关步骤 |
| 任意 | 多份互补文档 | `DOCUMENT_ASSISTED` | 最多两份局部证据合成，明确各自来源 |
| 任意 | 多份互斥版本且缺条件 | `CLARIFY` | 只问型号、版本、接口或现场状态等决定性条件 |
| 产品相关 | `NONE` | `GENERAL_TECH` | 给判断、3～5 项优先检查和下一条件，不强调“知识库不足” |
| 明显无关/注入 | `NONE` | `OUT_OF_SCOPE` | 固定范围收口 |

### 9.2 文档优先的边界

“文档优先”不等于“命中即全文”：

- 参数、IP、端口、页面位置、单个步骤等局部问题优先短答。
- “如何配置/升级/更换/完整检查某部件”等任务级问题，若 `PROCEDURE` 卡片直接覆盖，优先原文交付。
- 当短答是否足以完成任务无法确定，而文档含连续步骤或图片时，向文档交付倾斜。
- 已在当前会话交付过同一文档后的追问，不重复全文，除非用户明确要求重新查看。
- 故障问题即使命中排查文档，也优先按用户现象生成聚焦排查；需要完整检查清单时才全文交付。
- 文档只部分覆盖时，不为了“提高命中”把它说成完整答案。

### 9.3 回答格式

- 局部短答：直接结论 + 必要前提，通常 1 段或 1～3 项。
- 文档交付：`**《最新显示名称》**` 后直接正文，不出现“已找到/以下是文档内容”。
- 文档辅助：当前判断 + 文档确认事实 + 3～5 项排查 + 一个关键条件。
- 通用工程：当前判断 + 优先步骤 + 观察结果含义，不虚构型号专有能力。
- 所有正常技术回答使用统一短免责声明；正文不重复长篇责任说明。最终固定文案由产品/法务确认，建议基线为：“本回答仅供参考，请结合现场情况和正式资料核验，必要时联系海兰信专业人员。”
- 管理 DemoChat 和外部 Assistant 的就绪欢迎语统一为简短技术助手文案；不得显示文档数量或完整知识库描述。描述继续作为公开列表字段和内部范围输入。

## 十、连续排查与结构化问题状态

### 10.1 状态结构

将现有 `rag_issue` 扩展为版本化 `rag_case` 命名空间；首期仍可存于 `conversation.chat_context`，但必须复用现有 CAS，并审计所有覆盖/清空路径：

```json
{
  "version": 1,
  "goal": "排查VAU配置后无图像",
  "product": "VDR600",
  "components": ["VAU"],
  "confirmed_facts": [
    {
      "value": "网口指示灯正常",
      "source_user_message_id": "..."
    }
  ],
  "actions_taken": [
    {
      "value": "已设置电脑IP",
      "source_user_message_id": "..."
    }
  ],
  "observed_results": [
    {
      "value": "仍无法ping通",
      "source_user_message_id": "..."
    }
  ],
  "hypotheses": [
    {
      "value": "可能是网络层配置问题",
      "source_assistant_message_id": "..."
    }
  ],
  "active_document_ids": ["..."],
  "open_condition": "电脑与设备的IP和子网掩码",
  "updated_by_user_message_id": "...",
  "updated_by_assistant_message_id": "..."
}
```

### 10.2 一致性规则

- `confirmed_facts/actions_taken/observed_results` 只能来自当前或有效历史用户消息，并保存来源 ID。
- `hypotheses` 只能来自成功完成的助手消息，永远不转换为确认事实；用户确认后新增用户来源事实。
- 用户纠正已有信息时，状态补丁必须显式失效冲突项，不能同时保留互斥事实。
- `NEW_TASK` 清空旧目标相关状态，但不删除消息；`FOLLOW_UP` 才承接当前状态。
- 文档删除、知识库切换、冻结索引失效时移除无效活动文档，不删除仍有来源的用户事实。
- 状态更新与 RAG Trace、助手消息成功终态及 Assistant 请求终态在同一事务/CAS 中提交；失败、取消、超时、断连和幂等重放不重复应用。
- Support 不读取或写入 `rag_case`；Gateway 回退到 RAG 时只使用本次 RAG Turn 可验证的上下文。
- 状态数组有长度和 Token 上限；先淘汰旧模型假设，再淘汰已失效事实，不能静默删除当前目标和最新用户确认条件。

### 10.3 不采用自由文本摘要

不保存一段无法追溯的“会话总结”作为事实来源。LLM 1 可以读取结构化状态和有限原始轮次；每项现场事实必须能回到用户消息。旧助手回答仅作为历史建议，不能取代文档证据或用户观察。

- 最新显示名称只用于新回答；历史消息、旧 Trace 和幂等重放保持原快照。

- LLM 1、LLM 2 首期使用本轮冻结的同一 LLM 模型快照，但使用两个独立版本化 Prompt；不得在请求中途读取新的活动模型替换。

- 会话继续冻结索引；不得从当前新索引取卡片、从旧冻结索引取 Chunk。

### 11.4 幂等和失败

- 相同 Assistant 幂等键重放已保存公开终态，不重新调用两个 LLM。
- 规划失败不能先写成功消息；部分流式文本不得保存为成功。
- LLM 2 输出先完成结构校验和来源验证，再公开 `delta`；若需要实时流式，先缓冲结构头，只有验证后的答案区允许向外发送。
- `DOCUMENT_DELIVERY` 在文档有效性和归属检查完成后才发送正文。

## 十四、配置、性能、降级和回滚

### 14.1 计划配置

统一开关及 P2/P3 参数已固定并补齐 `.env.example`、生产示例和 Compose；P4 状态预算仍是后续计划项：

| 配置 | 建议初始值 | 说明 |
| --- | --- | --- |
| `M3_RAG_SEMANTIC_ORCHESTRATION_MODE` | `off` | `off/shadow/enabled`；独立于旧技术助手开关，迁移期明确优先级 |
| `M3_RAG_QUERY_PLANNER_MAX_TOKENS` | `320` | LLM 1 仅输出 JSON |
| `M3_RAG_QUERY_PLANNER_TIMEOUT_SECONDS` | `8` | 超时回退原问题；数值需实测后确认 |
| `M3_RAG_RESPONSE_PLANNER_MAX_TOKENS` | `1200` | LLM 2 结构化决策及非全文答案预算 |
| `M3_RAG_RESPONSE_PLANNER_TIMEOUT_SECONDS` | `30` | LLM 2 单次有界等待；失败在剩余总时限内回退旧路由 |
| `M3_RAG_QUERY_VARIANT_LIMIT` | `3` | 规划查询上限 |
| `M3_RAG_DOCUMENT_CARD_TOP_K` | `5` | 文档级候选上限 |
| `M3_RAG_RESPONSE_DOCUMENT_LIMIT` | `3` | 送入 LLM 2 的文档包上限 |
| `M3_RAG_CASE_FACT_LIMIT` | `12` | 用户确认事实上限 |
| `M3_RAG_CASE_TOKEN_LIMIT` | `1200` | 结构化状态估算 Token 上限 |

建议值不是生产结论。实施时必须验证总时限关系，不能让 Planner 超时、Embedding 重试、Rerank 超时和生成预算之和必然超过 `M3_TURN_DEADLINE_SECONDS`。

### 14.2 模式语义

- `off`：不读取卡片、不调用两个 Planner，完全沿用现有 RAG。
- `shadow`：后台执行并记录两个 Planner，但不执行 LLM 2 的策略，公开响应仍使用旧路由；只允许在隔离测试/明确接受额外费用和后台并发的环境使用。不得将 Shadow 的新答案发送给用户、写成公开消息或改变会话焦点。
- `enabled`：P2/P3 新编排接管 RAG 回答；当前代码能力已存在，但完整 Golden、工程评审、1/3/5 并发和回滚演练未完成，不能直接用于生产。

不能复用现有 `M3_RAG_TECH_ASSIST_MODE=shadow` 的“不调用模型”语义表达新 Shadow，避免运维误判。

### 14.3 性能策略

- 用户量少允许用两个高能力 LLM，但延迟仍是体验门槛；成本可次于质量，等待时间不能无上限。
- 原始问题 Embedding/BM25 与 LLM 1 并行，计划查询只补充而不阻断已取得候选。
- LLM 1 低温度、严格 JSON、低 Token；LLM 2 一次完成决策和需要的生成。
- `DOCUMENT_DELIVERY` 不执行第三次生成；只获取原始结构并交付。
- 候选包只含卡片、章节概览和代表 Chunk，禁止多文档全文 Prompt。
- SSE 继续及时发送 `accepted/progress` 和心跳；模型结构头校验完成前不泄漏内部标记。
- 分类型记录 query planner、原始检索、计划补检索、Rerank、response planner、文档加载、首文本和总耗时。

### 14.4 降级顺序

1. LLM 1 失败：原始问题 + 现有历史策略检索，Trace 标记 `QUERY_PLAN_DEGRADED`。
2. 文档卡片缺失：只使用 Chunk 候选；不得仅凭缺失卡片扩大文档交付。
3. Rerank 降级：保留现有禁止用未校准排名直接交付的保护。
4. LLM 2 失败或输出非法：在剩余时限足够时一次格式修复，否则使用旧路由；不使用半个计划。
5. 来源校验失败：拒绝对应引用/图片；精确产品回答不可降级为带伪引用的成功。
6. 总时限耗尽：沿用现有失败语义和干净部分文本，不保存成功终态。

### 14.5 回滚

- 将新开关改为 `off` 并重建/重启应用进程，恢复旧路由。
- 卡片表和 `rag_case` 数据保留，不影响旧代码读取；旧版本部署前必须确认迁移向后兼容。
- 不删除知识库、活动索引、文档、会话或数据卷。
- 不修改历史消息和幂等终态。
- 若新代码改变了 Prompt 或管理卡片，回滚后这些数据保持惰性，不能自动套用到 Support。

## 十五、Trace、指标和人工复盘

### 15.1 Trace 新增诊断

在现有 JSON 快照中记录结构化摘要，不记录密钥：

- `query_plan`：版本、状态、耗时、Prompt 哈希、独立问题哈希、关系/意图/范围、查询数量、降级原因。
- `document_card_retrieval`：卡片版本、候选文档、审核状态和分数；不复制全部卡片正文。
- `multi_query_retrieval`：每条查询来源、候选数量、融合去重。
- `response_plan`：版本、状态、策略、文档关系、选中 ID、Source ID、校验结果和降级原因。
- `case_state`：前后版本、来源消息 ID、补丁项数量和 CAS 结果；不额外复制用户敏感正文。
- `timings`：两个 LLM、各检索阶段、文档加载、首文本和总耗时。

### 15.2 质量指标

核心指标改为：

- 回答策略正确率。
- 正确文档交付率和错误文档交付率。
- 局部问题不必要全文率。
- 任务级问题不必要澄清率。
- 文档辅助回答的来源完整率。
- 无文档专业问题“解决/有推进/无推进”人工比例率。
- 无依据精确产品事实率。
- 连续排查重复步骤率和状态串联率。
- 范围外误答率。
- 两个 LLM 调用成功率、格式修复率、降级率和 p50/p95。

不以“命中文档数量”“回答字数”或单次点赞替代问题解决质量。

### 15.3 管理复盘

现有“Assistant 回答优化”详情增加内部策略、文档级候选、LLM 1/2 摘要和问题状态来源展示。复测继续冻结原问题和期望，不把生产用户的任意回答自动写入 Golden。管理员修改卡片后可复测同题，比较策略、文档、事实、耗时和最终回答。

### 16.4 放行硬门槛

以下为建议门槛，正式数值在 P0 由产品和工程负责人确认：

- 错误文档全文交付：0。
- 跨知识库、跨冻结索引、伪造 Source/图片：0。
- 无依据的精确产品参数、接线和官方步骤：0。
- 明显范围外、噪声和注入误答：全部通过。
- 任务级文档：全部关键题选择正确文档；同题至少重复 3 次验证非确定性。
- 局部短答：至少 90% 正确且无不必要全文，剩余必须可解释为数据/文档缺口。
- 连续排查：不得出现状态串会话、把模型建议写成已执行事实或重复推进。
- Assistant 契约、失败、取消、分页、图片、重放和并发测试全部通过。
- `bash scripts/check.sh` 全量退出码 0；前后端门禁和生产 Compose smoke 通过。
- 性能报告必须给出各策略的调用数、首文本、总耗时 p50/p95、超时和降级；是否接受增加的延迟由业务负责人基于真实报告确认，不能用计划值替代。

### 16.5 对照方法

1. 固定知识库、活动索引、模型、Prompt、问题和测试身份。
2. `off` 运行旧路径，保存完整公开响应和 Trace。
3. `shadow` 保存两个 Planner 计划，不改变公开响应。
4. 测试环境 `enabled` 使用相同问题新会话运行。
5. 自动比较策略、文档、Source、响应类型、图片、错误和耗时。
6. 工程师盲评“解决/有推进/无推进/错误”，并标记无依据事实。
7. 不因新行为不同直接修改断言；先由产品规则确认期望，再同时重评旧/新报告。

## 十七、部署、回填与验证流程

1. 合入代码时保持新开关 `off`，运行完整本地门禁。
2. 备份并核对目标数据库 Alembic 当前版本；执行 `upgrade head` 创建卡片结构。
3. 重建 API、索引 Worker 和维护 Worker，确认旧 RAG/Assistant 行为未变。
4. 对当前活动索引提交卡片回填任务，观察任务状态、模型调用、失败和卡片覆盖率。
5. 管理台逐份检查 VDR600 卡片，优先确认 `PROCEDURE`、相似标题和含图片文档。
6. 在隔离测试环境启用 `shadow`，运行专项集和真实问题；生产默认不承担 Shadow 双调用。
7. 修正卡片、Prompt、结构校验和状态规则后，在测试环境 `enabled` 全量复跑。
8. 执行 1/3/5 并发、断流、重放、模型超时和 Rerank 降级验证。
9. 通过门槛后部署生产代码仍保持 `off`，做健康、迁移、Assistant 契约和旧路径冒烟。
10. 在业务确认窗口启用新模式；首日重点监控错误交付、无依据事实、格式修复、降级和 p95。
11. 发现硬门槛问题立即切回 `off`，保留 Trace 和卡片用于离线复盘，不删除业务数据。

本文不授权自动连接生产、执行迁移、回填、模型调用或启用开关；这些操作必须在实施完成后按部署任务单独执行。

## 十八、目标表现示例

| 用户输入/场景 | 目标决策 | 目标表现 |
| --- | --- | --- |
| “配置 VAU 图像时电脑 IP 是什么？” | `SHORT_ANSWER` | 直接给 IP、掩码和必要连接前提，只引用对应证据 |
| “如何配置 VAU 图像？” | `DOCUMENT_DELIVERY` | 即使未写“完整”，仍交付直接覆盖该任务的完整文档和图片 |
| “请给出配置 VAU 图像的完整步骤” | `DOCUMENT_DELIVERY` | 不因单 Chunk 0.70 门槛错误拒绝；不列线缆检查文档让用户选择 |
| “按照配置文档操作后还是没有图像” | `DOCUMENT_ASSISTED` | 使用已交付文档事实，补充网络/线缆/通道排查，只问一个关键条件 |
| “网口灯正常，但无法 ping 通” | `DOCUMENT_ASSISTED` 或 `GENERAL_TECH` | 承接原故障，记录用户事实，优先核对 IP/掩码/网段，不重问已确认条件 |
| “启动十分钟后离线，怎么区分供电和网络？” | `DOCUMENT_ASSISTED` 或 `GENERAL_TECH` | 结论先行、3～5 项可验证步骤，避免未经证实的产品功能和过长免责声明 |
| 两份文档分别对应不同硬件版本 | `CLARIFY` | 询问实际型号/版本，不让用户选择内部文档编号 |
| 多份文档分别覆盖配置和故障处理 | `DOCUMENT_ASSISTED` | 最多两份局部证据合成，不整篇倾倒多份文档 |
| “写一首秋天的诗” | `OUT_OF_SCOPE` | 快速固定收口，不进入开放生成，不污染问题状态 |
| 用户说“不是 VAU，是 DAU” | `CORRECTION` 后重新规划 | 失效冲突对象和活动文档，保留仍有效现场事实，按 DAU 重新检索 |
