# 后台管理主链路改进执行计划

## 1. 目标

把当前分散在 Documents、Index Build、问题文档配置和 DemoChat 中的操作，收敛为一条不会绕过审核的管理链路：

```text
选择知识库
  -> 上传文档
  -> 后台构建候选索引
  -> 自动生成 Profile 草稿
  -> 管理员审核、驳回或改为 NONE
  -> 发布前验证
  -> 确认影响范围
  -> 原子发布
  -> 使用同一知识库进行问答验证
```

本次优先保证流程正确、状态明确和操作可追踪，不以视觉改版代替发布约束。

## 2. 已确认的问题

1. 候选索引已经被后端要求通过 Release 发布，但 Index Build 页面仍提供自动激活和直接激活入口。
2. 线上 Profile 仍能从管理页面直接保存，绕过草稿、验证和原子发布。
3. 同一知识库可以形成多个未完成 Release，旧候选缺少明确的 supersede 规则。
4. 当前知识库没有成为全局、持续可见的管理上下文；DemoChat 使用独立选择状态。
5. Dashboard 的无答案问题没有按当前知识库过滤，且切换知识库后指标不会刷新。
6. 上传完成后的构建、草稿生成和待审核状态只在局部页面可见。
7. Profile 审核没有展示置信度、生成理由和线上值对比，也没有可用的驳回入口。
8. Release 历史已经由后端返回，但前端只显示当前候选。
9. 状态组件没有覆盖 Release 和 Draft 状态，页面混用原始英文枚举。
10. “重复文档会生成新版本”的前端文案与后端实际的重复文件拒绝规则不一致。

## 3. 本次实现范围

### 3.1 发布链路约束

- 手工新建索引也默认进入候选 Release，不再从管理页面请求自动激活。
- Release 管理的 READY 索引不显示直接激活，改为跳转发布审核。
- 管理页面取消直接新建、编辑线上 Profile；线上列表改为只读，变更统一通过候选草稿。
- 创建新候选时，将同知识库旧的未发布候选标记为 `CANCELLED`，避免多个可发布候选并存。
- 发布事务再次确认不存在更新的开放候选，旧候选不能晚于新候选发布。

### 3.2 全局管理上下文

- 在所有后台页面顶部显示并允许切换当前知识库。
- 展示当前线上索引版本、候选状态和待审核数量。
- DemoChat 默认复用后台当前知识库；切换测试知识库时同步全局上下文。
- 使用 URL hash 保存当前管理页面，刷新和浏览器前进后退不再总是回到 Dashboard。

### 3.3 异步任务与 Dashboard

- 管理台在存在构建任务时进行全局轻量轮询，不要求管理员停留在 Index Build 页面。
- 上传后刷新候选工作区；构建完成后能看到待审核 Release。
- Dashboard 的无答案问题严格使用当前知识库过滤。
- 切换知识库时重新加载 Dashboard 指标。
- Dashboard 增加待审核候选、构建中和验证失败等管理待办摘要。

### 3.4 审核与发布体验

- 草稿列表展示生成来源、置信度和审核状态。
- 审核弹窗同时展示当前线上 Profile 与候选值，突出管理员实际决策对象。
- 增加“退回修改”；被退回草稿必须修改、重新生成或明确改为 `NONE` 后再批准。
- 重新生成全部草稿、单篇重新生成和最终发布增加确认提示。
- 发布确认展示知识库、索引版本、CREATE/UPDATE/NONE 数量和告警数量。
- 页面展示 Release 历史，但只有当前开放候选可操作。
- 补齐 Release、Draft、操作类型和就绪状态的中文状态映射。

### 3.5 稳定性

- 候选工作区加载失败必须显示错误，不能静默退化为“没有候选”。
- 知识库快速切换时丢弃过期响应，避免旧知识库数据覆盖新选择。
- 初始数据中单个非核心接口失败不阻止整个后台加载。

## 4. 本次明确不做

以下能力需要独立的数据模型或身份系统，本次只保留清晰边界，不以假数据模拟：

- 管理员账号、RBAC、审核人与发布人的可信身份审计。
- 已发布 Profile 完整快照和一键业务回滚。
- 文档 `logical_document_id`、版本号和 supersedes 关系。
- 在候选索引上运行完整 Support/RAG 行为回归的 Preview API。
- 多人会签、审核备注和工单指派。
- 批量上传与批量审批。

## 5. 后端实施步骤

1. 在创建非自动激活构建时，取消同知识库既有开放 Release。
2. 发布时在事务内检查是否存在更新的开放 Release。
3. 保留直接激活 API 作为兼容和运维能力，但管理前端不再对 Release 候选暴露该入口。
4. 保留 Problem Profile PUT API 兼容现有调用，但管理前端不再使用；后续 RBAC 项目再将其限制为应急权限。
5. 为 supersede、旧候选发布拒绝和普通候选发布补单元测试。

## 6. 前端实施步骤

1. 扩展 Store：全局页面导航请求、系统信息、候选派生状态、按知识库防竞态加载。
2. 改造 App Shell：全局知识库上下文、hash 导航和发布状态提示。
3. 改造 Index Build：统一候选构建、识别 Release 索引、跳转审核。
4. 改造 Documents：修正文案，上传后加载候选和展示下一步。
5. 改造 Dashboard：知识库范围、响应式刷新和管理待办。
6. 改造 Support Profiles：只读线上配置、草稿对比、退回、确认和历史。
7. 改造 DemoChat：复用全局知识库选择。
8. 完善状态映射、错误反馈和响应式上下文栏。

## 7. 验收标准

1. 管理页面不能直接激活绑定未发布 Release 的索引。
2. 管理页面不能直接写入线上 Profile。
3. 新候选产生后旧开放 Release 自动取消，旧候选发布被拒绝。
4. 当前知识库在所有页面持续可见，DemoChat 默认使用同一知识库。
5. 页面刷新后保留当前管理页面。
6. Dashboard 所有知识缺口数据均按当前知识库统计，并随知识库切换刷新。
7. 上传后无需停留在 Index Build 页面也能看到构建和待审核状态变化。
8. 管理员能看到草稿置信度、生成理由、线上值对比，并能退回修改。
9. 发布前显示明确的影响摘要并要求确认。
10. 可以查看历史 Release，但不能操作已发布或已取消版本。
11. 后端测试、静态检查、前端类型检查和前端完整测试全部通过。

## 8. 回滚策略

- 本次前端改动可按页面独立回退，不改变线上数据格式。
- 候选 supersede 使用已有 `CANCELLED` 状态，不新增数据库枚举和迁移。
- 若新候选创建失败，事务回滚，不会错误取消旧候选。
- 本次不提供已发布业务版本回滚；发布事务自身失败时仍由数据库事务恢复旧 Active Index 和 Profile。
