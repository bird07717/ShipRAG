# 技术决策记录（ADR）

本文件记录长期影响架构、维护方式或兼容性的决策。ADR-0001、0002 有本仓库中的直接规则或设计记录；ADR-0003～0005 是依据当前源码和迁移归档的已实现约束，原始决策记录、日期和取舍未在本次核查范围内找到，相关内容不得被解读为已证实的历史讨论。

## ADR-0001：以仓库内认知文档作为 AI 项目上下文入口

- 状态：已接受
- 日期：2026-09-02
- 影响范围：全仓协作与后续 AI Agent 任务
- 关联模块：`AGENTS.md`、`docs/ai/`
- 被哪项决策取代：不适用

### 背景

Agent 会话不保证保留历史记忆，且不同工具未必自动读取项目约定；项目包含前端、后端、迁移、部署与验收等多域信息。

### 最终决策

根目录 `AGENTS.md` 作为简洁入口、工作规则与按需路由；详细事实分域维护在 `docs/ai/`。每项改动在验证后进行认知影响检查。

### 决策原因

减少每次重新扫描仓库的成本，同时明确文档不能替代源码、迁移、配置和运行结果。

### 考虑过的替代方案

仅依赖聊天历史不可持久；将所有信息放在单一超长文件会降低检索效率、增加冲突与过时风险。

### 影响

后续任务需要先读 `AGENTS.md` 并按路由读取；架构、环境、数据模型、动态状态和已知问题的变化必须同步维护相应文档。

## ADR-0002：不在文档命中热路径增加在线 LLM 仲裁

- 状态：已被部分取代；RAG 范围由 ADR-0018 取代，Support 范围继续有效
- 日期：2026-08-28
- 影响范围：Support 文档路由与 RAG 回退
- 关联模块：`backend/app/support/`、`backend/app/rag/`、`docs/technical/llm-arbitration-deferred.md`
- 被哪项决策取代：ADR-0018（仅 RAG 文档选择与回答编排）

### 背景

文档命中 NO_MATCH 场景可增加在线 LLM 进行仲裁，但会引入新的延迟、非确定性和故障依赖。

### 最终决策

当前保持确定性规则路由为唯一决策来源；弱候选仅以提示/建议形式辅助后续交互，不自动交付。达到文档定义的 NO_MATCH 率或弱候选确认率触发条件后重新评审。

### 决策原因

本场景优先避免错误交付，并要求结果可审计、可回归；已有 LLM 依赖已用于生成、查询改写和离线 Profile。

### 考虑过的替代方案

在线 LLM 仲裁：当前未采用，因为没有替代规则兜底且增加热路径依赖。

### 影响

不得将 LLM 仲裁作为普通优化直接接入 `NO_MATCH` 路径；若重新立项，须采用独立开关、超时、降级和 A/B 验证。

## ADR-0003：RAG 索引发布与 Support Profile 发布使用独立生命周期

- 状态：已接受
- 日期：2026-09-02
- 原始决定日期：待确认（本次归档日期为 2026-09-02）
- 影响范围：知识发布、会话一致性、管理台
- 关联模块：`backend/app/ingestion/`、`document_profiles/`、`releases/`、`gateway/`
- 被哪项决策取代：不适用

### 背景

当前实现将技术索引与 Support Profile 置于不同的状态、表和发布指针中。原始决策背景待确认；本节不根据实现反推当时的业务原因。

### 最终决策

RAG 在技术构建成功后可激活索引；Support Profile 通过独立草稿、审核、发布和快照链路上线。会话冻结实际使用的索引/发布版本。

### 决策原因

待确认。当前实现的可观察结果是：RAG 索引可独立激活，Support Profile 需通过独立发布链路；会话保存所使用的索引/发布版本。

### 考虑过的替代方案

待确认。当前仓库未找到可验证的原始备选方案记录；不得将“单一原子发布”等可能方案写成实际讨论过的选项。

### 影响

排查和开发必须区分 RAG 活动索引、Support 活动索引/发布与会话冻结值；发布相关迁移和 API 契约不得假定它们同步变化。

## ADR-0004：为对外 Assistant API 设置独立认证与用户隔离

- 状态：已接受
- 日期：2026-09-02
- 原始决定日期：待确认（本次归档日期为 2026-09-02）
- 影响范围：外部集成、安全边界、会话与幂等
- 关联模块：`backend/app/api/assistant.py`、`assistant/`、`gateway/`、迁移 `0038`
- 被哪项决策取代：不适用

### 背景

当前实现提供独立的 Assistant 路由、服务凭据、外部用户 ID 和幂等请求表。原始决策背景待确认；本节不根据实现反推当时的权限评估。

### 最终决策

在 `/api/v1/assistant/*` 提供窄化接口，使用独立 `ASSISTANT_SERVICE_TOKEN` 并要求 `X-External-User-ID`；请求使用幂等记录，公开响应过滤内部字段。

### 决策原因

待确认。当前实现的可观察约束是：Assistant API 与管理 API 使用不同认证依赖，且请求按外部用户、知识库和幂等键隔离。

### 考虑过的替代方案

待确认。当前仓库未找到可验证的原始备选方案记录；不得将“复用管理 Token”等可能方案写成实际讨论过的选项。

### 影响

外部客户端不得持有管理令牌；生产部署和 smoke 都必须配置并验证 Assistant Token，且不能记录其真实值。

## ADR-0006：Assistant 对外上线状态与知识库运行状态分离

- 状态：已接受
- 日期：2026-09-11
- 影响范围：外部 Assistant、知识库管理、数据迁移
- 关联模块：`gateway/`、`api/assistant.py`、知识库管理页、迁移 `0041`
- 被哪项决策取代：不适用

### 背景

知识库原先只要处于 `ENABLED` 就会出现在 Assistant 列表中，导致新建但尚未完成索引和验收的知识库提前暴露；资源和历史入口也缺少独立发布边界。

### 最终决策

使用 `knowledge_base.assistant_online` 作为独立对外发布状态。迁移时保持既有启用知识库的可见性，后续新建知识库默认下线。Assistant 的列表、欢迎语、问答、会话、文档和图片入口共同执行上线状态、知识库状态与资源归属检查；列表的 `ready` 仍表示运行时完整就绪，不替代发布状态。其中文档原文入口后续由 ADR-0008 明确撤销，其他入口继续遵守该边界。

### 决策原因

在不改变现有 Assistant 路由及响应结构的前提下，阻止未验收知识库和已下线资源被已知 ID 绕过访问，同时保证现有生产知识库在迁移后不中断。

### 考虑过的替代方案

继续复用 `knowledge_base.status` 会混淆后台维护与对外发布；仅过滤知识库列表无法阻止通过已知会话或资源 ID 访问；迁移后将全部知识库默认下线会造成现有对接中断。

### 影响

所有新增 Assistant 知识库作用域入口必须复用同一发布边界。管理侧上线写操作和按知识库推荐问题已按 ADR-0009 实现；不得改变已经发布的外部 Assistant 契约。

## ADR-0007：部署环境的核心 RAG 模型缺少凭据时失败关闭

- 状态：已接受
- 日期：2026-09-11
- 影响范围：摄取、在线 RAG、生产配置、可观测性
- 关联模块：`core/config.py`、`ingestion/embedding.py`、`rag/rerank.py`、`services/rag.py`
- 被哪项决策取代：不适用

### 背景

生产环境缺少可用模型凭据时，Embedding 与 Rerank 的 `auto` 模式会静默使用 deterministic fake。线上查询向量因此可能与 Active Index 的真实向量空间不一致，fake Rerank 又只按输入顺序给出固定分数，使无意义输入也可能稳定命中文档。

### 最终决策

staging/production 禁止 M2 Embedding、M3 LLM、M5 Rerank 显式配置为 fake；`auto` 在环境和数据库模型快照均无有效凭据时失败关闭，不得回退 fake。开发/测试仍可显式使用受控 fake。在线 Trace 记录实际查询 Embedding provider/model，并保留 Active Index 模型字段用于一致性核查。

### 决策原因

生产返回明确的模型未配置错误比使用错误向量空间生成貌似正常但不可置信的文档命中更安全，也更容易通过健康检查和 Trace 定位。

### 考虑过的替代方案

继续允许 fake 并提高检索阈值无法解决向量空间不一致和伪分数问题；仅增加噪声词规则无法覆盖语义随机但形式正常的输入；启动时强制所有模型密钥存在会错误排除数据库加密模型快照这一合法凭据来源。

### 影响

部署前必须确保当前模型配置可由环境变量或可解密的数据库快照取得凭据，并与 Active Index 模型一致。缺少凭据时摄取或问答会明确失败；上线验证必须检查 Trace 实际 provider/model，不能只看配置行中的模型名称。

## ADR-0008：Assistant 不提供原文下载，文档名称作为可变展示元数据

- 状态：已接受
- 日期：2026-09-11
- 影响范围：外部 Assistant、文档管理、RAG/Support 回答展示
- 关联模块：`api/assistant.py`、`ingestion/`、知识库文档页、Assistant 对接文档
- 被哪项决策取代：不适用

### 背景

业务对接不再需要获得知识库原始文档，但管理员需要修正文档对外显示名称，并要求新回答中的标题与修改结果一致且区别于正文。

### 最终决策

删除外部 Assistant 原文下载接口，保留管理端原文访问和外部图片读取。管理端只修改既有 `document_source.display_name`；原始 `filename`、对象存储键、文档 ID 和索引内容保持不变，不触发索引重建。修改后的名称只作用于后续回答，既有消息、幂等重放和 Trace 不回写。回答正文中的文档标题使用 Markdown `**《文档标题》**`，结构化标题字段仍为纯文本。

### 决策原因

文档 ID 已是检索、Profile 和对象存储的稳定关联键，显示名称无需进入向量内容。保持历史快照不变可以避免不安全的 JSONB 与自然语言批量替换，并保留审计现场。

### 考虑过的替代方案

同步改名 MinIO 对象或重建索引会引入无必要的数据迁移和停机；重写历史回答无法可靠区分标题与正文；继续开放下载接口不符合当前业务边界。

### 影响

业务后台不得根据 `document_id` 拼接下载地址，只展示来源或加载图片。新建和重命名文档时应避免同一知识库内显示名称重复；标题格式变化属于 `answer` 的既有 Markdown 契约，不改变结构化字段类型。


## ADR-0009：采用轻量知识库上线检查与推荐问题管理

- 状态：已接受
- 日期：2026-09-11
- 影响范围：知识库管理、Assistant 欢迎语、迁移 `0043`
- 关联模块：`api/knowledge_assistant.py`、`assistant/configuration.py`、`KnowledgeAssistantSettings.vue`
- 被哪项决策取代：不适用

### 背景

小项目需要按知识库检查、上线和编辑三条推荐问题，用户明确选择简化流程，无需独立审批平台。

### 最终决策

采用管理员编辑、试问检查、确认上线；复用 `assistant_online`，增加每库问题 JSONB 和配置修订号。保存问题与上下线分别提供管理写接口，以行锁及修订号保证一致性。上线要求三条有效问题和当前策略就绪；下线不依赖模型可用。外部 API 路径和字段保持不变。

### 决策原因

满足知识库隔离、对外可见性和快捷问题运营需求，同时保留已有 Profile、索引、会话和 Assistant 认证边界。

### 考虑过的替代方案

审批状态机、独立发布快照、双人审核和不停服内容版本隔离：用户认为超出当前项目规模，本期不采用。

### 影响

试问是管理员人工检查，不承诺每个编辑值已自动回归通过；不冻结模型或知识索引。线上问题保存立即生效，运行配置变化后需管理员重新检查。历史线上库保持原问题，新库不继承全局例子。共享管理凭据不能识别独立审核人。

## ADR-0010：RAG 首轮优化独立于 Support，内容完整性先于放宽直达

- 状态：已接受（本地实现，生产尚未部署）
- 日期：2026-09-11
- 影响范围：RAG 首轮文档路由、公共 DOCX 摄取
- 关联模块：`rag/first_turn.py`、`services/rag.py`、`ingestion/`
- 被哪项决策取代：不适用

### 背景

本地实验复现聚合目标与最强块目标冲突，并发现 DC24V DOCX 中文文字图片未被摄取。保守单强阈值仅显示有限增益，二次文档重排没有证明额外直达收益。用户明确不混合 RAG 与 Support 问答链路。

### 最终决策

在 RAG 服务层实施冲突澄清和精确型号候选补召回，单强默认影子观察；不引入 Support 标准问题、标签或 Profile，也不降低共享路由门槛。所有直达交付完整文档，沿用现有会话版本与公开契约。旧式文字图片必须先验证内容与阅读顺序；当前无法可靠还原的浮动版式明确失败，不静默发布残缺或错序内容。解析结果以版本限制复用。

### 原因、替代方案与影响

优先避免错误交付，保留可追溯的诊断与关闭开关。未采用在线 LLM 仲裁、全库二次重排、无差别视觉描述加权或猜测浮动文字顺序。公共摄取保护同时影响两种模式；旧版本下一次构建需重解析，须预留成本并处理不兼容源文件。代码验证不代表真实模型质量验收，生产启用单强及候选索引激活均需后续验证。

## ADR-0012：用管理侧问题快照与隔离复测支持回答优化

- 状态：已接受
- 日期：2026-09-11
- 影响范围：管理台回答记录、人工标记、单题复测、迁移0044
- 关联模块：`assistant/reviews.py`、`assistant/retest.py`、`api/answer_reviews.py`、`AnswerReviewsView.vue`
- 被哪项决策取代：不适用

### 背景

已有指标与Trace可发现问题，但缺少记录预期结果、查看完整交付并验证修改的操作流程；用户要求按小项目规模实现第一批功能。

### 最终决策

### 原因、替代方案与影响

选择轻量管理流程，暂不建立复杂审批、自动调参或批量任务平台。未采用直接给Trace加标记并随日志删除的方式，因为人工确认的用例需要跨越短期保留窗口。记录只保存资源引用，不延长图片/索引寿命；多轮复测重问前文，缺失上下文或变化的澄清选择必须明确阻断。

## ADR-0013：原文交付完整性与模型预算分离

- 状态：已接受
- 日期：2026-09-11
- 影响范围：RAG 原文交付、Assistant 终态及历史快照
- 关联模块：`services/rag.py`、`assistant/service.py`、`api/assistant.py`
- 被哪项决策取代：不适用

### 决策与原因

原文交付直接复制已解析文档，不调用 LLM，因此不再套用交付 Token 截断预算。保留全文元素顺序、图片开关和既定标题去重，表格按既有 `table` 类型输出；普通模型问答继续保持上下文及超时限制。外部接口结构不变，不重新开放下载或增加分段续取接口，旧终态不重算。

### 替代方案与影响

仅提高阈值仍会在更长文档处丢步骤；新增分页交付需要更改调用流程，本次不采用。代价是完整 SSE 事件、历史页和持久化快照随文档增长，接入端需支持大事件并限制并发，后续容量评估不能被 fake 冒烟代替。源内容在摄取时的缺失仍须通过文档与候选索引验收解决。

## ADR-0014：以正文质量与同文档证据边界优化 RAG

- 状态：已接受
- 日期：2026-09-11
- 影响范围：RAG 生成、预算、Trace 与 Golden 评测
- 被哪项决策取代：不适用

### 决策与原因

文档命中不等于正文正确。Golden 保存完整公开响应并检查步骤、参数、表格和图片；对照用同一份断言重评两边。保留已有轻量管理记录/复测和脚本，不增加审核状态机或外部 Assistant 接口。

RAG 聚焦全文超预算时，只能在已确认文档及冻结索引中重新检索；沿用本轮查询向量并进行有界重排，无证据时拒答，不借用另一篇正文并标注原文档。片段按相关性保留，按阅读顺序展示；所有生成分支统一使用输入预算。实际生成计划与检索上下文分别记录，原文完整交付继续遵守 ADR-0013。

### 取舍与后续验证

文档内二次重排只发生于长文档降级，增加部分轮次延迟但不增加一次查询 Embedding。确定性来源校验不能证明每句话的事实正确，仍需源文档约束和人工评测。首轮事实问答复用 DOC_QA，默认 shadow，通过新配置显式试验；不因此放宽选文档规则，也不影响 Support 的共享文档路由。小样本对照不能作为全量开启或统计显著提升的证明。

## ADR-0015：通过分清依据恢复解释能力，沿用 Assistant 既有契约

- 状态：已接受
- 日期：2026-09-12
- 影响范围：RAG 提示词、首轮解释、流式呈现和错误收口
- 被哪项决策取代：不适用；补充 ADR-0014

### 决策与原因

产品参数、操作和故障判定仍须正文证据；LLM 可以组合事实、进行计算和条件分析，补充明确标注的通用原理及待验证假设。文档事实与推断/通用内容混合使用现有 PRODUCT_EXPLAINED，纯通用内容不返回文档引用。只提供必要的小节，不强迫简单解释展开成完整操作模板。现象改善不能自动推出无需更换或维修成功。

## ADR-0016：RAG 历史采用显式完整轮次与焦点边界

- 状态：已被 ADR-0019 取代（显式完整轮次保留，RAG 焦点边界将淘汰）
- 日期：2026-09-12
- 影响范围：RAG 多轮上下文、Prompt 预算、Trace、迁移 `0045`
- 关联模块：`rag/history.py`、`rag/repository.py`、`rag/prompt.py`、`services/rag.py`
- 被哪项决策取代：ADR-0019；当前代码仍保留本实现，直至 V2 落地

### 决策与原因

RAG 历史只使用显式关联、双方成功完成、属于当前焦点代次的完整用户/助手轮次。用户陈述原样保留但标为未核实，旧模型回答标为非事实证据；不增加摘要模型、事实抽取或长期记忆。文档切换只桥接触发确认的用户原问题，不带入旧焦点回答。消息数、历史 Token 和总 Prompt 三层预算均按完整轮次裁剪，且总预算先放弃最旧历史再减少当前证据。

新轮次在 `message` 保存配对，旧 Assistant 可复用 `assistant_request`，旧内部记录没有可靠信息时排除而不猜测。Trace 只保存消息 ID 与裁剪诊断。模型证据使用最新文档显示名称，只在元素身份及前缀可证明时删除短开头标题，不全局改写正文。外部 Assistant 与 Support 契约保持不变。

### 取舍与后续

排除不可靠旧数据会让部分升级前内部会话失去上下文，但可避免把不相关答案当事实；`legacy` 仅作为运行时回退。确定性选择和 Prompt 分区不能验证现场陈述真假，也不能替代真实多轮质量评测。若将来需要语义压缩，应另行设计可追溯摘要、失效和纠正机制，不能直接覆盖原消息。

## ADR-0017：小体量 RAG 技术助手的分层回答与轻量问题状态

- 状态：已被 ADR-0019 取代（产品范围与通用工程边界保留，回答分支与 `rag_issue` 将淘汰）
- 日期：2026-09-13
- 影响范围：RAG 回答计划、提示词、问题状态与结果收口；Assistant 既有契约不变
- 关联：[优化执行方案](../technical/rag-technical-assistant-optimization-plan.md)
- 被哪项决策取代：ADR-0019；当前代码仍保留本实现，直至 V2 落地

### 背景

用户少、单库文档覆盖有限，主要用户是工程师和专业人员，更关心实际问题能否推进。当前可靠命中后的整篇交付、仅首轮部分问法的短答，以及目录导向的无命中处理，不能充分发挥 LLM 的工程解释与排查能力。

### 决策

在 RAG 内分开文档选择、回答形式和依据等级：完整操作保留原文图表，局部/解释问题有据生成，无可靠文档但仍属产品技术范围的问题通过 `DOMAIN_ASSIST` 使用通用工程知识给出原因分析、检查步骤、预期结果和条件分支。知识库是正式产品事实依据而不是回答门槛；不按接线、电气、升级或拆装主题自动拒答，但常见值和假设不能冒充当前产品事实，通用回答附免责声明及必要谨慎提醒。

自由度仍受产品领域约束。明显无关问题使用既有 `OUT_OF_SCOPE`，明显噪声前置短路，提示注入不能改变角色、范围、引用或保密规则；产品与无关任务混合时只回答产品部分。首期由确定性门禁和同一次生成的内部模式前缀收口，不增加串行分类模型。

首期复用已有且对 Assistant 调用方公开的 `knowledge_base.description` 表达用户可见的产品范围，不新增内部描述字段。管理平面补创建后编辑和乐观并发检查；`RagRepository.begin_turn` 在知识库和索引锁定快照中统一读取名称/描述，直入及回退 RAG 共享该 Turn，避免入口分别读取。空描述不让整个知识库失效，也不影响有据问答，但不得开放弱/无命中的宽泛通用回答。描述修改不重建索引，从后续新请求生效；Trace 记录范围更新时间及哈希，历史回答不重算。若将来确需不可公开规则或独立审批，再另行评审内部范围字段。

原始历史继续按完整轮次和焦点边界选择；首期状态只保存原问题、回答形式和一个待确认条件，并审计全部覆盖路径、CAS 和成功终态事务。完整用户观察、助手建议和无进展状态根据真实复盘再立项，不增加摘要模型或长期记忆。

### 替代方案与取舍

仅开启事实短答不能覆盖确认和无命中问题；无限开放模型会变成通用聊天并放大无关回答，继续默认拒答又不能满足专业用户。采用有领域边界的单次生成、小模块、统一回退开关、动态免责声明、现有管理标记及验收脚本。短答和领域分析会增加生成延迟，模式前缀缓冲会略微推迟首文本；收益与误放行必须用真实多轮验收共同证明。

### 实施与生效条件

本地已实现统一开关、范围快照、管理端说明编辑、回答形式策略、`DOMAIN_ASSIST` 流式收口，以及只承接一个条件且与成功终态同事务提交的 `rag_issue`；复用既有字段，无新增迁移，外部 Assistant 契约不变。代码、示例环境和生产 Compose 均默认 `off`。

生产启用前仍须通过真实模型主集/专项集、工程师语义评审、Assistant/Support 契约和低并发性能验收；出现专有事实虚构、无关回答、引用越界或状态串联时回退 `off`。完整问题状态和多文档事实合成属于后续独立实验，当前单文档降级约束保持不变。

## ADR-0018：RAG 采用文档级理解与双 LLM 语义编排

- 状态：已被 ADR-0019 取代（P1 文档卡片保留；P2 可重构复用；P3 六策略与 P4 状态不再继续）
- 日期：2026-09-13
- 影响范围：RAG 文档理解、查询规划、检索、回答决策、连续排查、管理审核和 Trace；Assistant 公开契约保持不变
- 关联：[RAG 文档智能与双 LLM 语义编排执行计划](../technical/rag-semantic-orchestration-execution-plan.md)
- 被哪项决策取代：ADR-0019；Support 继续遵守自身路由和发布边界

### 背景

当前 RAG 已具备混合检索、Rerank、完整文档/图片交付、有据问答和受控通用工程回答，但文档选择主要由 Chunk 聚合及固定阈值完成，回答形式主要由确定性问法规则完成。LLM 通常在这些决策之后才参与生成，无法稳定利用文档整体任务、用户真实目标和连续现场状态。真实小样本中，VAU 完整配置问题的目标文档聚合明显领先，仍因最佳 Chunk 未达下限进入 `UNCONFIRMED`；局部 IP 问题能够正确短答，说明需要保留多种回答形式，而不是统一全文或统一生成。

### 决策

RAG 新增独立于 Support 的版本化文档卡片和文档级检索，用于表达文档类型、任务、组件、适用问题、前提和排除范围；Chunk 级检索继续负责具体证据。卡片绑定知识库、冻结索引和文档，显示名称仍从 `document_source` 动态读取。自动卡片必须结构校验、记录内容指纹和模型/Prompt 快照，并支持管理员审核；新结构通过 Alembic 创建，回填不得在迁移事务中调用外部模型。

在线 RAG 使用两个职责不同的 LLM 阶段。LLM 1 根据当前问题、可追溯会话状态和知识库范围输出有界查询计划，识别新任务、追问、纠正、问题范围和最多三条检索查询；原始问题检索尽量并行保留。检索融合文档级卡片与现有 Chunk 候选后，LLM 2 在候选白名单内判断文档关系、选择回答策略并在需要时生成答案。LLM 2 同时完成决策和生成，不再增加第三次在线回答调用；完整文档由后端按冻结索引读取，模型不得重写原文。

内部策略统一为局部短答、完整文档、文档辅助、通用工程、澄清和范围外，并映射现有 Assistant `ANSWERED`、`DOC_DELIVERED`、`UNCONFIRMED`、`OUT_OF_SCOPE`。局部参数/位置/单步骤问题仍短答；任务级问题与 `PROCEDURE` 文档直接匹配时提高原文交付优先级，不要求必须出现“完整”；故障和解释问题优先聚焦回答；无可靠文档但属于产品范围时允许通用工程分析。已交付同一文档的追问不重复全文。

连续排查使用带来源消息 ID 的版本化 RAG 问题状态，分开用户确认事实、已执行操作、观察结果和模型假设；状态补丁与成功消息、Trace 和 Assistant 终态在同一事务/CAS 提交。Support 不读取或写入该状态，不复用 Support Profile、标签或标准问题。

### 决策原因

文档级任务选择与 Chunk 级取证是不同问题，继续从局部 Chunk 分数推断整份文档会在相似文档、宽泛任务和多轮排查中形成结构性误判。当前用户量少且面向专业用户，允许以额外模型成本换取任务理解、文档判断和工程扩展能力；稳定性由结构化输出、候选白名单、来源校验、冻结快照、独立开关、旧路由降级和真实评测提供，而不是依赖相同模型重复投票。

### 替代方案与取舍

仅改文档名称可以改善标题和 Rerank，但不改变既有 Chunk 向量/BM25，也不能表达文档类型、任务和排除范围。继续调整阈值或正则实现简单，但会累积特例并在放宽直达时增加错误交付。每轮只用一次生成模型延迟较低，却无法在检索前规划并在检索后统一判断。复用 Support Profile 会重新耦合已经明确分离的 RAG/Support 生命周期，因此不采用。

两个在线 LLM 会增加延迟、费用、非确定性和上游故障面；文档卡片增加迁移、回填与管理成本。原始检索并行、LLM 1 小型 JSON、LLM 2 决策与生成合并、候选预算和统一总时限用于控制开销，但不能在实施前承诺性能不下降。

### 实施与生效条件

新能力使用独立 `off/shadow/enabled` 开关。`off` 完全沿用当前实现；`shadow` 只在明确接受真实模型费用和延迟的隔离环境记录新计划，不改变公开响应；`enabled` 才接管 RAG，旧路由作为模型/结构校验失败时的降级。生产启用前必须完成文档卡片回填与审核、自动化全量门禁、真实模型新旧对照、工程师语义评审、Assistant 契约和 Support 隔离验证、1/3/5 并发性能报告及回滚演练。

截至 2026-09-14 已完成 P0/P1：交付 `0046` 卡片结构、结构化离线生成、索引冻结 Embedding、显式回填任务、管理编辑/审核、乐观并发和删除/GC 一致性。VDR600 活动 Index v39 已只读复核为预期 42、`READY/CONFIRMED` 42，`AUTO/REJECTED/FAILED/STALE/MISSING` 均为 0，`shadow_ready=true` 且 `ready=true`。迁移不调用模型，卡片生成失败不阻塞索引。

P2 已交付查询 Planner、原始/独立/计划查询去重、文档卡片与 Chunk 多查询检索、RRF 文档候选融合、严格同库/冻结索引过滤、降级和 Trace。独立问题与查询在 Trace 中只保存哈希、长度、分类及计数。`shadow` 的后台任务不占用公开旧回答等待时间，完成后独立合并诊断；补充 Embedding 失败保留原问题候选。4 个真实代表问题的查询计划和目标文档首位召回均通过，但完整 Golden 和并发尚未执行。

P3 已交付严格响应 Planner、候选文档/Source/引用白名单、六策略执行器和诊断持久化；`shadow` 在 P2 后继续后台生成 LLM 2 计划，但不执行策略或修改公开状态，`enabled` 才接管 RAG。模型预留的状态补丁在 P3 被忽略，完整 `rag_case` 仍属于 P4。真实 Shadow 已证明两个 Planner 不阻塞公开旧回答；真实 GLM 最终三轮 Enabled 代表题全部通过，但调试轮次存在 Planner/Embedding 超时及结构化输出波动，故生产仍不得启用 `enabled`；需在 P5 完成完整 Golden、工程师语义评审、1/3/5 并发和回滚演练。Support 保持独立，不读取文档卡片、两个 Planner 或未来 `rag_case`。

## ADR-0019：RAG 改为每轮重检索的隐藏全文双 LLM 生成链路

- 状态：已接受；V0～V5 已部署，V6 为可选数据库清理。2026-09-18 补充中“厂商、正式分类及精确型号参数没有依据时不得猜测确定值”一句已由 ADR-0029 部分取代
- 日期：2026-09-14
- 影响范围：RAG 查询理解、文档检索、完整上下文、回答生成、图片、会话历史、Trace、配置和旧代码退出；Support 保持独立
- 关联：[RAG 隐藏全文双 LLM V2 执行计划](../technical/rag-full-document-generation-v2-execution-plan.md)
- 取代：ADR-0018 的 P2/P3/P4 在线形态；扩展并最终取代 ADR-0016/ADR-0017 在 RAG 路径中的焦点历史、原文交付和分层回答实现

### 背景

现有 P3 让 LLM 2 根据每篇最多两个有限 Chunk 判断整份文档关系、六种回答策略和最终答案，完整文档只在选择 `DOCUMENT_DELIVERY` 后由后端直接展示。真实验收出现错误全文交付、局部回答不足、通用回答引用泄漏和结构化字段降级。Query Planner 的精确标识正则又把普通英文词视为型号，遗漏纯数字型号，并不能正确处理斜线复合别名。

当前知识库规模小，一份文档通常围绕一个问题，文档内 Chunk 强相关。继续细化首轮、单强、事实、解释、焦点停留、切换确认和全文交付规则，会增加相互影响而不能让最终模型获得完整问题上下文。

### 决策

RAG 每轮执行同一流程，不再区分首轮和焦点追问。LLM 1 只负责从当前问题和最近完整问答还原独立问题、生成少量补充查询及判断产品范围；原始问题始终参与检索。Chunk 与 RAG 文档卡片负责召回并聚合到文档，前 1～3 份同库、同冻结索引候选的有序完整元素作为隐藏上下文交给 LLM 2。

2026-09-18 补充范围所有权与扩展边界：LLM 1 是产品范围决定的唯一来源，LLM 2 不得以“候选文档没有直接覆盖”为由重新把 `IN_SCOPE` 判为范围外；`UNCERTAIN` 优先回答或只问一个关键条件，只有 LLM 1 的 `OUT_OF_SCOPE` 可以形成公开范围外终态。服务端确定性归一化两阶段冲突，不增加第三次模型调用，并在 Trace 记录模型原始 kind 与最终 kind。知识库名称和管理员维护的公开说明是可信产品档案，可直接支持产品身份、用途和范围回答；相关文档仍是产品专有事实的优先证据，但不是回答许可证。范围内无直接文档时允许专业通用知识继续给原理、原因、排查顺序和下一步；厂商、正式分类及精确型号参数没有产品档案或文档依据时不得猜测确定值。

LLM 2 统一生成短答、操作说明、故障分析、通用工程帮助或一个关键问题，不再决定是否向用户交付整篇文档，也不接受 LLM 1 预先给出的回答深度分类。它根据当前问题、任务历史和完整候选正文生成最小充分回答：事实问题直接答，操作问题即使用户未说“完整”也覆盖完成任务所需步骤，局部追问不重复整套流程。公开 RAG V2 正常结果使用既有 `ANSWERED` 及结构化 `content`，只展示答案和正文定位的白名单图片，不展示完整原文、候选列表、来源元数据或文档总数；外部 `references` 允许为空。文档标题、文件名和正常技术编号不是秘密，可按解决问题需要出现在正文。服务器只对文档/图片归属白名单、Prompt 结构、管理面 URL 和对象存储位置等真实实现信息做确定性检查，避免宽泛正则误伤多数回答。

LLM 1、LLM 2 和其他结构化工具调用默认关闭内部思考。LLM 2 及其一次合规修复保留可配置的有界思考实验能力；显式开启时，DashScope/Qwen 使用独立 2048 Token 思考预算，最终回答继续使用既有 4096 Token 和 45 秒时限。该默认值取代早期“LLM 2 默认开启”的短期实验设置：开启后的定向样本没有与关闭模式形成同题 A/B，不能证明稳定质量增益，而已确认延迟明显增加。其他 Provider 只在已知支持时启用，不臆造跨供应商预算协议。Qwen 思考模式不叠加不稳定的 JSON Mode，最终内容仍按 Prompt Schema 本地校验并沿用既有一次修复。供应商推理正文只由传输层忽略，不保存到 Answer、Message、Trace 或 Assistant 响应；Trace 只记录是否请求思考、配置预算及普通 Token 用量。该能力不增加新的模型阶段。

多查询 Chunk/卡片先以 RRF 聚合到有限文档池，再复用既有 Rerank Provider 对标题、已确认卡片和代表 Chunk 做文档级排序；失败时保留 RRF 原顺序，不增加第三次 LLM。IP、版本、带单位数值和端口的证据匹配只进入 Trace 观测，不参与拒答、修复或改写。技术通用能力优先于宽泛参数硬门禁；硬失败保留给跨库文档/图片、无效 D/I 白名单、Prompt 结构和无证据的真实内部实现信息。

RAG V2 不读取或写入 `focus_document_id`、`focus_index_id`、`focus_epoch`、待选文档或 `rag_issue`，也不实施 `rag_case`。会话上下文使用显式关联且成功完成的最近完整问答轮次，按轮次和 Token 裁剪；旧 Assistant 回答可用于还原指代，不能成为产品事实依据。每轮重新检索，换题不会被旧焦点锁定。

短追问和纠正由 LLM 1 显式输出 `relation` 与 `active_task`；LLM 1 只接收一份按轮次组织的成功历史，任务只从最近完整轮次的用户请求继承，不从旧助手回答建立产品事实。任务锚点参与本轮查询召回、文档级 Rerank 和 LLM 2 选证。为降低短追问重新检索漂移，`FOLLOW_UP/CORRECTION` 且存在任务锚点时，最近成功回答实际使用的最多 3 份文档可作为零初始分软候选加入本轮文档级 Rerank；服务器仍校验同知识库、同冻结索引、`document_source.status='STORED'` 与 `index_document.status='READY'`。软候选不加分、不锁定、不保证进入前 1～3 份全文，明确换题 `NEW_TASK` 完全不继承，因此该机制不是旧焦点的恢复。有效 V2 的准备阶段只冻结轮次和参数，不执行 legacy 预检索；本轮所有去重查询只批量嵌入一次，避免两套检索结果交叉污染。

2026-09-18 补充上游波动边界：LLM 1 单次时限调整为 25 秒，429/5xx/连接类即时失败最多快速重试一次，完整超时不重试。解释器失败时仅对“存在最近完整成功轮次、当前是省略对象的短追问且没有明确新操作/产品”的输入确定性恢复上一轮用户任务；恢复结果仍走当轮检索、同库冻结索引校验和文档级 Rerank，不锁定答案，也不恢复旧焦点状态机。其他失败继续使用原问题。两阶段 Prompt 同时约束混合输入只处理产品技术子任务，忽略无关创作、娱乐或闲聊要求；不为具体问题文本建立运行时词表。

V5 后 RAG V2 是开发、staging 和 Production Compose 的唯一代码路径，不再存在 `M3_RAG_PIPELINE_MODE`。V2 内部降级使用原问题、词法候选或有界通用回答，不跳转到已删除的旧路由。旧首轮、焦点、Query Rewrite、Query/Response Planner、六策略和 RAG 原文交付已物理删除；回滚只能使用旧 Git 提交或旧镜像。

### 关联一致性约束

完整文档和图片必须由服务器按 `knowledge_id + frozen index_id + document_id` 加载；模型只选择本轮 D/I 别名。首次 SSE 完成、保存消息、Assistant 历史和幂等重放必须使用同一公开终态。`include_images=false` 在保存前过滤。Trace 只记录哈希、ID、数量、预算和耗时，不复制全文。

`conversation.focus_*`、`chat_context`、`support_context_version` 与 `message.focus_epoch` 仍被 Support/Gateway 使用。V2 先停止 RAG 读写，不清空数据、不修改历史 Alembic；只有 Support 完成独立迁移并经过至少两个发布周期零旧列读取，才允许评估删列。Support→RAG 回退不得把 Support 焦点当作 RAG 文档授权。

### 取舍与实施条件

完整候选文档能减少局部 Chunk 缺证，但会增加 LLM 输入、数据处理范围、延迟和上下文干扰；必须限制文档数和总 Token。LLM 生成仍可能遗漏步骤或改写参数，因此“看过全文”不能代替完整操作 Golden 和工程师评审。文本模型只能根据图片 caption/OCR 选图，若需要观察像素需另行引入多模态回答。

P1 文档卡片、冻结索引、混合检索、Rerank、完整元素读取、图片资产和 Assistant 幂等继续复用。V0～V5 已建立唯一 V2 链路、非焦点完整轮次历史、任务继承、双入口一致生成、单一检索所有权、文档级排序、多文档证据覆盖和公开边界，并删除旧运行时代码与配置。Support 专用路由策略已移入 `app.support` 并冻结；共享数据库字段和历史迁移按 V6 条件保留。质量验收看整体解决率和关键错误，不为单条非关键模型波动添加问题文本、标题或编号特判。详细阶段、配置、测试门槛和回滚条件以关联执行计划为准。本决策不授权生产部署或清理业务数据。

## ADR-0020：PDF 直接解析入库，content_revision 按格式版本化

- 状态：已接受（本地已实施于 feat/PDF 分支，真实 PDF 样本验收待执行）
- 日期：2026-09-15
- 影响范围：文档上传校验、摄取解析、REUSE 复用判定、管理台上传入口
- 关联模块：`backend/app/ingestion/parser_pdf.py`、`validation.py`、`models.py`、`pipeline.py`、`repository.py`、`services/ingestion.py`、`DocumentsView.vue`
- 取代：ADR-0011（交付行为部分）

### 背景

知识库存在大量 PDF 文档，形态为单栏正文 + 设备照片栅格图 + 页眉/页脚（公司 Logo 与页码），无表格。备选方案是先转换为 DOCX 再走现有解析器。

### 决策

PDF 直接解析入库，不做 PDF→DOCX 转换：pdf2docx/LibreOffice 转换普遍产出绝对定位文本框与浮动图片，正是 DC24V `LEGACY_FLOATING_TEXT_LAYOUT` 的已知失败形态，等于系统性制造最差输入；且 pdf2docx 依赖 AGPL 的 PyMuPDF，LibreOffice 子进程与只读根文件系统 Worker 容器的运维/安全代价高。直接解析（pdfplumber，MIT）一次跳变、按坐标保证阅读顺序、图文自然交错，页眉/页脚用位置 + 跨页重复启发式在输出前剔除（区域内一次性内容保留）。

`content_revision` 从全局版本号改为按格式分派：DOCX 保持 `ooxml-vml-1`，PDF 为 `pdf-1`。构建计划期与执行期的 REUSE 判定均按文档自身格式的期望版本比较，升级一种格式的解析器不会触发另一种格式的全库重解析与重嵌入费用。

图片解码支持 DCT（原样 JPEG）、Flate（colorspace/bits 重组 + SMask 合成转 PNG）、JPX；不支持的编码或损坏图片使整份构建明确失败（沿用 ADR-0010 不静默发布残缺内容的原则）；小于 16px 的装饰性小图跳过并告警。加密 PDF 上传即拒绝。PDF v1 不产 TABLE 元素：语料无表格，检测启发式有误判风险；若未来出现表格，文字仍按行提取入库，以新的 PDF 版本号触发重解析。

正式 OOXML 页眉/页脚是独立部件，DOCX 解析器从不读取，无需处理；正文内重复 Logo 的清理不纳入本决策（避免破坏 VML 文字恢复机制）。

### 影响

上传链路按扩展名分发：`.pdf` 走 PDF 校验（魔数、加密、`m2_pdf_max_bytes` 100 MiB、`m2_pdf_max_pages` 200）与 `source.pdf` 对象键；DOCX 路径行为不变。分块、嵌入、图片富化、索引持久化、检索与问答链路全部复用，不感知来源格式。无数据库迁移（`document_source.mime_type` 列已存在）。`index_document.metadata` 的 `mammoth_warnings` 键泛化为 `parser_warnings`。生产部署前须先用真实 PDF 样本执行候选索引构建与人工核验（元素顺序、图片数量、页眉剔除效果、检索质量），通过后才激活。

## ADR-0021：Support 优先运行模式冻结，运行边界按 RAG_ONLY 设计

- 状态：已接受（2026-09-15 用户确认）
- 日期：2026-09-15
- 影响范围：`engine_runtime_policy`、`chat_execution_mode`、Assistant 请求自动恢复、问答轮次准入闸门
- 关联模块：`backend/app/core/config.py`、`backend/app/tasks/assistant_recovery.py`、`backend/app/common/turn_gate.py`

### 背景

系统保留 RAG 与 Support 双引擎及 `SUPPORT_WITH_RAG_FALLBACK` 运行策略，但用户于 2026-09-15 确认 Support 优先模式已冻结、不再使用；实际运行均为 RAG_ONLY。RAG 轮次由 `M3_TURN_DEADLINE_SECONDS` 的总时限严格包络；Support 轮次的结构化调用在轮次时限包络之外（`complete_structured` 最多两次尝试、每次最长 provider timeout），且 Support 路径没有独立总时限。

### 决策

- Support 优先仅作为代码兼容路径保留，不作为运行模式使用；默认与部署配置均为 RAG_ONLY。
- 运行时限、容量与自动恢复边界按 RAG_ONLY 设计：`ASSISTANT_REQUEST_STALE_SECONDS` 只需大于轮次时限（Settings 校验器强制）。若未来重新启用 `SUPPORT_WITH_RAG_FALLBACK`，必须先把该边界提高到 `2 × M3_PROVIDER_TIMEOUT_SECONDS + M3_TURN_DEADLINE_SECONDS` 以上（校验器注释已标注），并重新评估准入闸门的持有时限假设。
- 生产各知识库 `engine_runtime_policy` 是否存在 Support 策略行未逐一核对（待确认）；启用前应先检查并切换。

### 影响

准入闸门、自动恢复、监控指标与文档均以 RAG_ONLY 为前提；Support 代码与测试保持可编译可回归，但不作为容量或时限验收对象。V5 将原 `app.rag.doc_router` 的共享决策代码移至 `app.support.document_routing_policy`，RAG 不再导入；这属于冻结和隔离，不代表删除 Support 数据、接口或数据库字段。

## ADR-0022：图片级解码失败降级为跳过告警，同文档同错误构建重试上限 2 次

- 状态：已接受（2026-09-16 实施）
- 日期：2026-09-16
- 影响范围：PDF 解析器、索引构建管线、构建失败计数、文档列表 API、管理台文档页与构建详情
- 关联模块：`backend/app/ingestion/parser_pdf.py`、`pipeline.py`、`repository.py`、`api/schemas.py`、`DocumentsView.vue`、`IndexBuildView.vue`
- 取代：ADR-0020 中"不支持的编码或损坏图片使整份构建明确失败"的条款；ADR-0010 的"不静默发布残缺内容"原则在图片维度降级为显式告警

### 背景

真实语料出现 WPS 导出/扫描仪固件生成的 PDF，其图片 XObject 字典使用规范内联图像缩写滤镜名（`/Fl`、`/CCF` 等）。pdfminer 能按缩写解压数据，但解析器白名单只认全名，导致数据已成功解码仍被"不支持的图片编码 Fl"拒绝，整库构建中止；且失败构建自动触发 followup、REUSE 只认活动索引，形成每轮全量重跑的无限空转（与 DC24V 文档同一故障模式）。同时任务错误不含文档名，管理员无法定位问题文档。

### 决策

1. **滤镜缩写名归一化**：`Fl→FlateDecode`、`AHx→ASCIIHexDecode`、`A85→ASCII85Decode`、`LZW→LZWDecode`、`RL→RunLengthDecode`、`CCF→CCITTFaxDecode`、`DCT→DCTDecode`，归一化后走既有白名单；`CCF/LZW` 仍属不支持编码。
2. **图片级失败降级**：单张图片解码失败（含不支持编码、损坏数据、SMask 失败）跳过该图片并记录 `PDF_IMAGE_SKIPPED: 第N页…` parser_warning，文档其余文本与图片继续；结构性问题（加密、损坏文件、页数超限）仍整体失败。文本完整性不再被单张图片劫持。
3. **同文档同错误重试上限**：文档处理失败时查询历史（`count_document_build_failures`：同 KB + 同文档 + 同 error_code 的 FAILED 计数），达到 2 次后该文档在当轮构建中标记 `SKIPPED`（含文件名与原因），其余文档继续，构建可成功；跳过清单写入任务 `metadata.skipped_documents`。`_finalize_index` 容忍 SKIPPED（要求至少 1 份 READY），`document_count` 只计 READY。文档级确定性失败（如 DOCX 浮动版式）从"瘫痪整库"变为"缺一份 + 显式告警"。
4. **可观测性**：`list_documents` 以 LATERAL join 附带最近一次构建的 `last_build_status/last_build_error/last_build_version`；文档页对 SKIPPED 文档显示告警（需重新处理+原因）；构建详情失败时显示 `current_document`。

### 影响

`index_document.status` 新增 `SKIPPED` 值（VARCHAR 列，无迁移）。解析器修订号不升级：既有 READY 结果未受本缺陷影响（带缩写滤镜的 PDF 从未成功入库），修复只影响此前失败的文档。跳过文档进入成品索引的语义为"部分索引"：激活后检索不覆盖该文档，由告警驱动人工修复重传。若全部文档被跳过，构建失败（"索引存在未完成文档"）。

## ADR-0023：Assistant 上线要求活动索引的 RAG 文档理解全部确认

- 状态：已接受（2026-09-17 本地实施）
- 日期：2026-09-17
- 影响范围：Assistant 管理发布、公开知识库就绪态、欢迎语与问答前置检查
- 关联模块：`backend/app/gateway/repository.py`、`assistant/configuration.py`、`KnowledgeAssistantSettings.vue`
- 扩展：ADR-0009 的“当前策略就绪”上线条件

### 背景

RAG V2 同时使用 Chunk 和文档理解卡片进行文档级召回。索引可正常检索不代表自动生成的卡片已经过人工核对；如果允许卡片缺失、失败、过期、拒绝或仍为 `AUTO` 的知识库直接对外，会把未审核的文档路由元数据带入正式 Assistant。

### 决策

Assistant 上线与持续对外可用必须满足活动索引中全部有效文档的 RAG 文档理解已确认。有效文档定义为同知识库、活动索引中 `index_document.status='READY'` 且 `document_source.status='STORED'` 的文档；合格卡片必须匹配当前 Schema，且为 `generation_status='READY'`、`review_status='CONFIRMED'`。零份有效文档同样不满足门禁。

该条件并入 `assistant_runtime_blockers`，由管理发布、公开知识库列表、欢迎语和 Chat 统一复用。它不并入通用 `get_readiness()` 或引擎策略更新，因此管理员仍可在独立 DemoChat 中生成、审核和验证未上线内容。已上线后发生状态漂移时不自动改写 `assistant_online`，而是动态返回 `ready=false` 并拒绝新欢迎语/问答；全部确认后自动恢复，避免隐藏的发布状态写入和额外状态机。

### 取舍与实施

该门禁提高正式对外文档选择的可控性，但新增知识库、切换索引和显式重生成卡片都必须完成逐份确认，运营步骤增加。Assistant 列表当前按库计算完整就绪态，新增聚合查询仍保持线性查询规模；知识库扩展到数十个或列表频率显著上升时按既有已知问题评估批量快照或短缓存。外部 API 路径和字段不变，仅扩展 `ready` 语义；无新迁移或环境变量，依赖既有 `0046` 卡片结构。

## ADR-0024：索引构建重试与中止改为人工决策，删除按对象前缀整清

- 状态：已接受（2026-09-17 实施，待生产部署）
- 日期：2026-09-17
- 影响范围：索引构建管线、任务取消、索引状态机、GC 与单索引删除、任务记录保留
- 关联模块：`backend/app/ingestion/pipeline.py`、`tasks/ingestion.py`、`tasks/recovery.py`、`services/ingestion.py`、`ingestion/repository.py`、`api/ingestion.py`、`tasks/repository.py`、迁移 `0047`、`frontend/src/views/IndexBuildView.vue`
- 取代：自动 followup 重试机制（原 `create_followup_build_if_needed` 三处触发点全部移除）

### 背景

自动 followup 在 REUSE 只认活动索引的机制下意味着每轮全额模型成本，且管理员无知情权：VDR600 三轮全量空转、51% 构建无法停止是两次实际损失。构建运行中没有任何中止手段，坏文档只能烧完整库；失败索引的删除依赖资产记录逐个清理，硬崩溃遗留的无记录孤儿对象（v43 事故实证）无法回收。

### 决策

1. **失败即停**：构建失败（含 worker 崩溃后的孤儿回收）不再自动排 followup。`rebuild_required` 在失败/取消时重新置位，作为唯一"待重建"事实源由管理台徽标持续提示；重试由管理员通过索引管理页"重建"按钮触发（后端 `POST /indexes/{id}/retry` 原有端点，白名单扩至 `CANCELLED`）。ADR-0022 的同文档同错误 2 次跳过熔断保留，计数由手动重试推进，第 3 次构建自动跳过坏文档完成其余。
2. **运行可中止**：INDEX_BUILD 接入既有协作取消（`POST /tasks/{id}/cancel` 白名单扩容）。取消是任务行终态转换，构建循环在文档边界轮询（`_update_task` 带 `status IN ('QUEUED','RUNNING')` 守卫，进度心跳不会把 CANCELLED 擦回 RUNNING）；排队期取消在管线入口短路，不消耗模型调用；激活事务一旦开始不中断。索引与未处理文档落 `CANCELLED` 终态（迁移 `0047` 同时补上 ADR-0022 遗漏的 `index_document` `SKIPPED` 约束值——该路径此前从未执行，一触发即会撞 CHECK 约束崩溃）。
3. **CANCELLED 与 FAILED 同权**：可删除（GC 保留策略同样适用）、可重试；CANCELLED 文档不进失败计数（计数器过滤 `status='FAILED'`），手动重建不被取消历史惩罚。冻结会话无风险——取消的构建从未激活，不可能被指针引用。
4. **删除按前缀整清**：图片对象键结构 `indexes/{index_id}/documents/...` 天然按索引前缀组织，单索引删除与 GC 改为标记 DELETING 后按前缀扫删全部对象再删数据库行。不依赖资产记录，硬崩溃孤儿一并清除；中途失败索引停留 DELETING 由 GC 自愈重试。文档原件与 `document_source` 不受索引删除影响。
5. **任务记录保留**：`task_record_retention_days=90`（0=永久），周期 GC 扫描修剪终态超期记录，每库保底最新 10 条，活动记录绝不动。

### 取舍与实施

瞬态故障（如 embedding 短暂不可用）不再自愈，需人工点一次重试——管理台有失败通知与徽标，可预测成本优于自动空转。手动重试推进熔断计数意味着跳过坏文档需要管理员点两次"重建"，按钮文案明确提示该语义。"停止"的粒度是文档边界：正在处理的文档（OCR 重的可能分钟级）会完成，其余立即停止。二期候选：REUSE 来源放开到 CANCELLED 索引实现真断点续跑（同哈希同修订才复用，构造上安全），需单独立 ADR 评估"只信生产验证结果"不变量的放宽。

## ADR-0025：RAG 理解卡片跨版本复用与一键确认

- 日期：2026-09-18
- 状态：已实施（提交 `badeaad`）
- 影响范围：RAG 文档卡片生成链路、内容指纹语义、文档管理页
- 关联模块：`backend/app/rag/document_cards.py`（指纹）、`rag/document_card_repository.py`（copy_cards / confirm_auto_cards）、`tasks/ingestion.py`（构建后复制）、`api/rag_document_cards.py`（confirm-batch 端点）、`frontend/src/views/DocumentsView.vue`

### 背景

卡片按 `(index_id, document_id)` 唯一存储，每次构建新索引版本后全量重新生成——即使 32 份文档中 31 份未变更且摄取层已全部 REUSE（分块/向量零模型成本）。生产卡片生成 32/32 LLM 失败证明该环节爆炸半径等于全库文档数。`content_fingerprint` 混入 `index_id`，同内容跨索引指纹必然失配，跨版本复用在指纹层面被锁死。

### 决策

1. **卡片跨版本复制**：构建成功后把 REUSE 文档（摄取层判定的 `build_mode='REUSE'`）的卡片行——含 `routing_embedding` 向量与 `review_status`——从上一版索引复制到新索引；生成任务现有的"指纹匹配即跳过"逻辑据此只为新增/变更文档调用 LLM。复制源取 `IndexBuildResult.prev_index_id`（pipeline 运行时快照），与摄取层 REUSE 判定同源，构建期间人工切换活动指针不会错位。
2. **指纹语义修正**：`content_fingerprint` 去掉 `index_id`——指纹是内容变更检测，index_id 不是内容。存量卡片指纹失配会在下次生成任务中自愈（跳过不命中 → 重新生成），无需数据迁移。
3. **审核状态跨版本保留**：CONFIRMED 跨版本保留（老内容不再要求重看），AUTO 留待人工确认，REJECTED 复制后继续挡 readiness（"上次明确拒绝、内容未变"）。FAILED/STALE/过期 `schema_version` 卡片与 REBUILD 文档不复制，留给生成任务。
4. **一键确认**：`POST .../rag-document-cards/confirm-batch` 单事务把当前索引全部 READY/AUTO 卡片置 CONFIRMED（`revision+1` 保持乐观锁链），REJECTED/FAILED/缺失不动，响应携带最新 readiness。与复用配合后，新增一个文档的确认成本从 N 份降到 1 份。

### 取舍与实施

向量复用依赖 REUSE 三条件（同 embedding 模型/文件哈希/解析器修订）保证维度与语义一致，构造上安全。复制失败只记日志、构建照常成功，卡片任务退化为现状全量生成（天然回滚路径）。确认与生成任务并发时，后完成的 `save_generated` 会把该卡置回 AUTO，前端确认后刷新 readiness 即可发现残余。schema_version 升级发布时旧卡自动失效重新生成，与既有语义一致。

## ADR-0026：在既有双 LLM 中增加保守的 Knowledge/Conversation 二路由

- 日期：2026-09-23
- 状态：已被 ADR-0027 修订（保留二路径、Trace 与历史隔离；废弃“新判断必进检索”的边界）
- 影响范围：RAG V2 Query Interpreter、第二阶段生成、技术历史、Trace 与管理指标
- 关联模块：`backend/app/rag/v2/query_interpreter.py`、`conversation_answer.py`、`pipeline.py`、`history.py`、`rag/repository.py`、`rag/metrics.py`

### 背景

纯寒暄已经能在 LLM 前确定性短路，但“同意联系专业人员检查”“谢谢”“你能做什么”“把刚才回答压缩成三点”等输入既不适合继续扩充关键词规则，也不应被强制注入文档并回答成新的技术问题。新增第三次模型调用或复杂多意图状态机会扩大时延、故障面和维护成本。

### 决策

保留两阶段模型结构，不新增第三个模型阶段。Query Interpreter 在原结构化职责末尾增加必填二值 `response_path`：`KNOWLEDGE` 完整复用既有检索、文档上下文与技术 LLM 2；`CONVERSATION` 跳过 Embedding、检索、Rerank 和文档加载，改用同一 LLM 快照及独立的短回答 Prompt。Conversation 只覆盖确认/同意、致谢/反馈、结束、能力介绍，以及不新增事实地改写、压缩或总结最近技术回答；只要包含新事实、判断、原因、步骤、参数、诊断、安全建议、服务事实或混合技术任务，均为 Knowledge。只有 `scope=IN_SCOPE` 且不携带检索查询/约束时，Conversation 才能生效；`OUT_OF_SCOPE`、`UNCERTAIN`、结构化字段缺失/无效或字段冲突均由服务端保守回退 Knowledge，继续沿用既有范围收口。沿用现有结构化输出修复和瞬态重试，因此异常情况下实际供应商请求次数仍可能超过两次，但不会增加新的语义处理层。

纯寒暄等既有确定性门禁保持零模型调用。Conversation LLM 2 不得产生引用、图片、链接或声称检索文档；模型、结构化或公开输出失败时使用固定简短回应，不回跳 RAG。路径写入 `citation_result`、终态/进度 Trace、Usage 和 `message.rag_history_context`；Conversation 轮次保留在审计与运营总量，但排除技术历史、技术质量和 RAG 延迟样本。外部 Assistant/SSE 响应结构不变，无数据库迁移或新模型配置。

### 取舍与实施

LLM 1 增加了一个二值判断，因此不能声称对其零影响，也不会减少 LLM 1 调用次数；收益是避免非知识输入被迫构造检索意图，并节省后续检索、重排和文档上下文成本。误判为 Knowledge 主要增加成本，误判为 Conversation 会损害正确性，因此所有服务端兜底向 Knowledge 倾斜。第一版不承接开放域闲聊、一般工程常识或厂商服务事实。2026-09-23 定向真实 Assistant Golden 最终统一复跑 8/8：三个范围外冲突全部恢复为 `OUT_OF_SCOPE`，两个纯寒暄命中零模型门禁，致谢、能力介绍和同意联系海兰信三个用例均为 Conversation 且检索 `SKIPPED`；完整 55 案例/77 轮技术集仍待复跑后才能建立生产基线。

## ADR-0027：按文档依赖路由非文档回答，保持 LLM 1 单一解释职责

- 日期：2026-09-24
- 状态：本地实施，真实回归进行中
- 影响范围：RAG V2 Query Interpreter、非文档 LLM 2、技术 LLM 2 的证据边界、Golden Set
- 修订：ADR-0026 的 Conversation 适用范围与“新判断必进检索”准则

### 背景

真实问答中，“是否需要联系工作人员”是一般性人工协助建议；用户确认当前产品文档未把联系厂商定义为该故障的必需处置。旧准则因问题要求新判断而强制检索，会把不相关板卡文档或统一免责声明误作联系依据。针对具体措辞增加正则特例又会分散路由权、放大维护成本。

### 决策

保留一次 LLM 1 和二选一的第二阶段，不新增模型调用或技术会话状态。LLM 1 输出独立请求、范围、任务关系、当前任务及唯一的 `response_path`；删除模型生成的补充检索查询和约束，由服务端从原问题、独立请求和任务锚点确定性构造检索输入。`KNOWLEDGE` 用于产品专有事实、参数、技术操作/诊断、官方服务事实和明确询问文档规定的请求；`CONVERSATION`（兼容现有 Trace 名称）扩展为无需文档依据的回答，包括确认、能力介绍、改写既有回答及一般性沟通/人工协助建议。需要作出新判断本身不是检索条件；无法确定是否依赖文档时保守走 Knowledge。删除新增的能力、同意、改写、联系人员句式正则及事后追问关系归一化，不靠第二字段覆盖 `response_path`。

非文档 LLM 2 可以给有条件的一般建议，但不能声称检索或引用资料，不能把历史回答和统一免责声明当成文档规定，也不能承诺代用户联系或编造官方渠道。技术 LLM 2 回答“资料是否规定”时，候选未见限制不能推断允许自行操作或安全；实际模型是否始终遵守须由真实 Golden 和人工复核确认。Conversation 轮次仍排除后续技术历史与 RAG 质量/延迟样本；外部 Assistant 契约不变，无数据库迁移。

## ADR-0028：两处沿用已久的信任边界写成显式决定

- 日期：2026-09-29
- 状态：已接受（记录既有实现，非新代码行为）
- 影响范围：`app/common/turn_gate.py`、管理图片资源端点、对外 Assistant 图片资源端点
- 关联模块：`backend/app/common/turn_gate.py`、`backend/app/api/ingestion.py`、`backend/app/api/assistant.py`、`backend/app/gateway/repository.py`

### 背景

代码 Review 复核发现两处一直存在、但从未在认知文档中显式定性的行为，均属于"当前规模下正确，扩展后可能失效或被误读为漏洞"的隐藏假设：

1. `turn_gate.py` 的并发限流用进程内 `asyncio.Semaphore` 实现，按事件循环隔离。docstring 已写明"生产进程假设只有一个事件循环"，但这一假设的后果（多副本部署会让限流失真）没有写进任何面向运维的文档。
2. 管理台图片资源端点 `GET /api/v1/image-assets/{id}/content`（`app/api/ingestion.py`）不校验图片所属文档的软删除状态或知识库上下线状态，任何有效管理凭据可读取任意图片；对外 Assistant 的同名端点 `GET /api/v1/assistant/knowledge-bases/{kb}/image-assets/{id}/content`（`app/api/assistant.py`，实现见 `gateway/repository.py:assistant_image_asset`）则严格要求文档 `STORED`、知识库 `ENABLED` 且 `assistant_online`。两者权限范围的差异此前只是代码事实，未被记录为有意设计。

### 决策

**并发限流**：维持进程内信号量不变，不引入跨进程/跨副本的分布式限流（如 Redis 计数器），因为当前生产只有一个 backend 容器实例，引入分布式协调的复杂度和延迟成本高于现有收益。但把"扩容为多副本时 `CHAT_TURN_CONCURRENCY_LIMIT` 会变成每副本各自计数、总限流上限随副本数线性放大"写成显式已知限制，作为未来扩容前必须处理的前置条件，而不是留在源码注释里等人踩到。

**图片端点权限不对称**：维持现状，不收紧管理端点。管理凭据（`service_token`）本身代表对整个管理面的信任（可读写知识库、文档、索引、模型配置），额外校验单张图片的文档/知识库状态不会提升实际安全边界，反而会妨碍管理员查看已下线知识库或已删除文档的历史图片（例如排查、审计场景）。对外 Assistant 凭据（`assistant_service_token`）代表外部业务后端的窄权限，必须与"用户只能看到当前已发布、未删除内容"的外部契约保持一致，因此保留严格校验。

### 取舍与实施

不改变任何现有代码行为，只是把两条隐含假设提升为记录在案的设计决定，避免：（a）未来扩容 backend 副本时限流静默失真且无人知晓原因；（b）安全审计或新成员阅读代码时把管理图片端点的宽松校验误判为需要修复的漏洞。若未来管理面凭据模型改变（例如引入按角色细分的管理权限），应重新评估图片端点是否需要与角色权限对齐；若 backend 扩容为多副本，应在扩容前把 `turn_gate` 改为基于 Redis 或数据库的跨进程计数器，或改用反向代理层限流。

## ADR-0029：证据分层——面向专业用户有界放开行业通用知识

- 日期：2026-09-30
- 状态：已接受（已提交，未部署）
- 部分取代：ADR-0019 在 2026-09-18 的补充中，“厂商、正式分类及精确型号参数没有产品档案或文档依据时不得猜测确定值”一句；“LLM 1 是范围决定唯一来源、服务端不发起第三次调用”保持不变
- 影响范围：`backend/app/rag/v2/answer_generator.py` 回答策略第 2、6、7、10 条与新增第 11 条，`query_interpreter.py` 产品范围定义；Golden 证据边界组与 `backend/app/rag/evaluation.py` 的 `content_forbidden_patterns`

### 背景

2026-09-29 本地真实复验（`ta_evidence_*`）显示，原策略与模型行为相反：问厂商/认证时，LLM 2 遵守“不得补充厂商、正式分类”的规则返回范围外，每次都落入 `SCOPE_CONFLICT` 固定反问；问 IP 等级、工作温度时，模型大多仍给出数值，只是附了核验提示，有时还写“根据产品规格”或编造手册章节。产品用户都是专业工程人员，用户明确希望发挥 LLM 的扩展能力。

### 决策

把“没有依据就不说”改为“可以说，但必须标明依据层级”：

1. 依据分三层：检索文档、管理员维护的产品档案、行业通用知识。前两层可以表述为本产品信息；第三层只能用“行业通常/一般/典型”等措辞，并说明资料未提供。
2. 厂商、产品类别、适用标准或认证属于产品范围，应直接回答，未写明时给出该类产品的行业通用情况。
3. 没有文档依据的参数分两类：防护等级、工作温度、存储时长、适用标准等规格类信息可给行业典型值（先说明资料未提供，并引导以铭牌或正式资料为准）；电压电流额定值、接线端子定义、端口号、IP 地址、固件版本和升级条件等说错会导致误操作或损坏设备的事实，仍不得给出具体值。
4. 硬红线：来源必须真实，不得把通用知识写成本产品规格或手册内容，不得编造文档、手册或章节名称。
5. 义务类问题：“未见规定”仍不等于“文档允许”，但可另起一句给出标注为专业建议的处理建议。

### 取舍

模型给出的典型值本身可能不准，因此用“只能引用文档”的例外名单兜住高后果参数，并以 Golden 证据边界组持续测量；闲聊路径（`conversation_answer.py`）不放开，仍不得提供未经核实的产品技术事实。若放开后误导性典型值在生产反馈中出现，应先收窄规格类清单，而不是回到全面禁止。

## ADR-0030：回答阶段只读 LLM 1 的标准化问题

- 日期：2026-09-30
- 状态：已接受（已提交，未部署）
- 修订：ADR-0019 中 LLM 2 同时接收用户原话 `current_question` 以保留否定/纠正的做法；否定与纠正改由 LLM 1 的 `relation=CORRECTION`、`active_task` 和 `resolved_question` 表达
- 影响范围：`answer_generator.build_answer_prompt`（移除 `current_question`）、`query_interpreter.py` 规则、`validation.scrub_document_keys`、`pipeline.py`

### 背景

LLM 1 已把问题整理成可独立理解、去掉无关附加任务的 `resolved_question`，但 LLM 2 仍读用户原话，于是重复理解问题：原话里的“顺便写首诗”需要额外规则压制，规则一多就互相干扰（ADR-0029 放开后写诗回归到 3/4），LLM 2 的职责也越来越重。同时，放开来源表述后，模型在正文中写出内部文档编号的比例升到 12%。

### 决策

1. 职责划分：LLM 1 负责理解（标准化问题、范围、关系、任务、路由）；LLM 2 只回答标准化问题（选证据、定篇幅、标依据层级）；服务端负责确定性校验和清理。LLM 2 不再接收用户原话，服务端仍用原话判断参数是否由用户提供。
2. LLM 1 的 `resolved_question` 必须原样保留用户给出的现场条件、数值、否定、纠正和回答形式要求，只去掉无关附加任务。LLM 1 降级时 `resolved_question` 回退为原话，因此 LLM 2 保留一句“不执行与产品技术任务无关的附加要求”作为兜底。
3. 内部文档编号用确定性清理而不是重生成：只改写本轮分配过的编号的括号引用和“文档/资料+编号”写法，原文中出现的同名标号不动；不增加模型调用，不会因此导致回答失败。

### 取舍

LLM 1 的改写错误不再能被 LLM 2 纠正，且自由文本形式的形式要求可能被丢弃：2026-09-30 本地实测“三点简要说明”4/4 保留，但英文作答要求只有 1/4 保留。若需要稳定支持回答语言等形式要求，应以结构化字段（而非自由文本）从 LLM 1 或确定性检测传给 LLM 2。
